## Этап 1. Фундамент `frontend-v2/` (низкий риск, ничего не ломает)

**Что делаем:** отдельный каталог `frontend-v2/` рядом с `miniapp/`. Собирается отдельно, в прод **не попадает**.

- Vite + React + TypeScript.
- `@tma.js/sdk-react` (3.0.23, MIT, React 17–19, репо в официальной организации `Telegram-Mini-Apps`). Проверено через `npm view`; альтернативы отклонены: `@twa-dev/sdk` 8.0.2 без обновлений с 2025-02, `@vkruglikov/react-telegram-web-app` мёртв с 2023-12, пакета `@twa-react` не существует.
- Токены R03 → TS-слой (единственный источник, см. `DESIGN_SYSTEM.md` §1).
- API-клиент: пор `miniapp/js/01-utils.js:43-177` почти дословно (`mintSession`, `authHeaders`, `withSessionResilient`, `friendlyError`).
- Генерация TS-типов из `app/api/contracts/` через `openapi-typescript`.

**Почему отдельный каталог:** новая сборка не пересекается с `miniapp/`, старый интерфейс остаётся единственным раздаваемым. Никаких изменений в `app/api/main.py` на этом этапе.

**Приёмка:** `npm run build` в `frontend-v2/` успешен; `tsc --noEmit` чист; ES токенов совпадает со значениями R03 §2.1 (сверка таблицей, не на глаз); `miniapp/` не тронут; CI зелёный.

**Риски:** заменить `innerHTML`-рендер на React — главный объём. Не переносить imperative-JS без адаптации (см. `REUSE_MAP.md` §«Что не переносить дословно»).

## Этап 2. Сквозной чат на `POST /api/chat/oracle` (backward-compatible)

**Что делаем:** реализовать единый диалог и убедиться, что авто-роутизация работает.

- Единственная точка отправки: `POST /api/chat/oracle` — тот же `DEFAULT_AGENT`, но с полным ответом.
- **Не `/api/ask`:** это compat-ручка (`app/api/routers/chat.py:51-61`), отдающая только `{answer, questions_left, allowance}` — без `routing`, `proof`, `thread_id`, `charge`. Диагностики, на которой строится вся сценaрийность v2, в ней нет.
- Ответ содержит `routing`, `proof.tools_used`, `thread_id`, `charge` — на их основе рисуем сцену и мягкую маркировку. **Никакого «передала вопрос Урании».**

**Две обязательные правки backend (минимум необходимого):**

1. **CORS — не добавляется.** Задача CORS решается **Vite dev proxy**, а не middleware в продакшене. Причина: `CORSMiddleware` с разрешённым origin'ом расширяет поверхность атаки прода, и делать это ради удобства локальной разработки — неверный размен. Конфигурация (`vite.config.ts`):
   ```ts
   server: { proxy: { '/api': 'http://localhost:8080', '/static': 'http://localhost:8080' } }
   ```
   В dev запросы идут на тот же origin, который проксирует Vite → CORS не возникает.
   **В проде сборка раздаётся тем же origin** (`miniapp/dist/` через `GET /`, см. Этап 3), поэтому cross-origin не возникает и там. `CORSMiddleware` остаётся отсутствующим — как сейчас.
   Единственное исключение: если разработка пойдёт против удалённого API с другого домена, тогда и только тогда — middleware с **точным** origin'ом (никогда `*`), включаемым флагом окружения.
2. **rate_limit и `X-Session-Token`.** `app/api/deps.py:75-88` определяет идентичность только из `x-init-data`/`dev_user`, иначе `ip:{host}`. Клиент с токеном под NAT получает общий лимит (write 30/мин, llm 12/мин на всех). Нужно, чтобы guard понимал заголовок токена.

Обе правки — аддитивные, не меняют контракт и не затрагивают auth.

**Приёмка:** вопрос через `/api/chat/oracle` возвращает ответ; при вопросе про Таро в `routing.agent` приходит `tarot`; cross-user тест на `/api/chat/oracle`; существующие `test_api.py`, `test_agent_routing.py`, `test_bus200_replay.py` остаются зелёными.

**Риск:** без правки rate_limit реальные пользователи под общим IP упрутся в лимит — найти до открытия.

## Этап 3. Подключение новой сборки в прод (обратимо, флаг)

**Что делаем:** Vite-output пишется в `miniapp/dist/` под тем же контрактом имён; `miniapp/index.html` заменяется минимальной оболочкой.

**Точные требования к сборке:**
- `build.outDir` → абсолютный путь к `miniapp/dist`.
- Имена: `app.[hash:12].min.js` и `app.[hash:12].min.css` — **должны матчиться regex `^app\.[0-9a-f]{12}\.min\.(js|css)$`** (`scripts/check_frontend_build.py:22-24`).
- `output.entryFileNames`, `assetFileNames` аналогично; `manualChunks: undefined`.
- Перезаписывать `miniapp/dist/manifest.json` теми же ключами (`js`, `css`).

**Точные требования к `index.html`:** оставить ровно один `<link rel="stylesheet" href="/static/styles.css?v=N">` и один `<script src="/static/js/entry.js?v=N"></script>`. Причина: `_miniapp_index_body()` (`app/api/main.py:345-347`) подставляет bundle двумя regex — по шаблону CSS-ссылки и по строкам `<script src="/static/js/...?v=N">`. Всё, что не матчится, останется в HTML как есть.

**Три CI-скрипта требуют правок — иначе миграция оставит CI красным при рабочем коде:**

| Скрипт | Проблема | Правка |
|---|---|---|
| `scripts/check_frontend_build.py:30-35` | Требует, чтобы число `<script>` в index.html **равняло** `manifest.jsFiles` | Переписать под реальную сборку Vite |
| `scripts/check_frontend_provenance.py:6-9` | Жёстко читает `miniapp/js/01-utils.js`, `10-chart.js`, `12-misc.js` и `miniapp/css/15-ritual-redesign.css`; при их удалении упадёт на `read_text` | Перевести ключи провенанса в новое расположение |
| `scripts/check_static_asset_references.py` | Проверяет существование `/static/...` литералов | Работает и с `.ts`/`.tsx` (`TEXT_EXTENSIONS` расширен) — оставить как есть |

**Переключение без простоя:** раздать новый HTML при наличии сборки, иначе — старый. Никакого fail-closed на этом этапе: в проде старый путь продолжает работать, новый включается флагом окружения.

**Приёмка:** `npm run build:frontend` → `check_frontend_build` / `check_frontend_provenance` / `check_static_asset_references` зелёные; `tests/test_api.py:965` (хешированный бандл в проде) проходит; `/`, `/survey`, `/admin` открываются — они обслужены `app/api/main.py:350-369,372-387` и не требуют правок.

**Риски:**
- `miniapp/dist/` в `.gitignore` и **локально отсутствует** → в `APP_ENV=production` приложение упадёт на `_validate_production_config` (`main.py:104-113`). Это fail-closed и так задумано, но при миграции означает: сборка обязательна до переключения.
- Кэш-контракт: `/static/dist/<hash>.min.*` → `immutable` год; `/static/*` → час. Не ломать эту логику (`main.py:283-297`).

## Этап 4. Маршрутизация (проектное решение, не код)

**Проблема:** SPA-fallback отсутствует. `GET /{filename}` (`main.py:398`) — catch-all на один сегмент, отсекающий `/`, `\` и ведущую `.` (это защита от `..%2F.env`, не трогать). Запрос `/chart` вернёт JSON 404.

**Варианты:**
1. **Hash-режим роутера** (`/#/chart`) — ноль изменений backend. Дёшево, работает в вебвью.
2. **Явные роуты** (`/chart`, `/people`) — требуют регистрации роутов в `main.py`, отдающих тот же `_miniapp_index_body()`.
3. **SPA-fallback хендлер** — самый гибкий, но меняет поведение catch-all и требует осторожности с защитой от path traversal.

**Рекомендация: вариант 1 (hash-режим).** Минимум изменений, нет риска для catch-all, нет новых поверхностей. Глубинке ссылки из бота (`/survey`) уже работают как есть.

**Приёмка:** прямой заход по любой ссылке отдаёт приложение, а не 404; catch-all по-прежнему отдаёт 404 на `/..%2F.env`.

## Этап 5. Единый Oracle (продуктовая суть)

**Frontend:**
- Убрать экран выбора проводника и онбординг-intent.
- Всегда `POST /api/chat/oracle`.
- Убрать авто-переключение чата и «Передала вопрос {имя}» (`miniapp/js/07-chat.js:856-859`, `routingHtml`).
- Заменить на мягкую маркировку по `proof.tools_used`: «посмотрела в карту», «вытянула карты».

**Backend:**
- Allow-list инструментов из intent, а не из `spec.skills` (`runtime.py:129`). Механизм frozenset сохраняется, источник меняется.
- Лимиты per-domain: `risk_level: high` и жёсткие лимиты Миры (20с / 4 хода / 6 вызовов) становятся свойством домена «хиромантия», а не персоны.
- Поле `agent` в `shared_context` переосмыслить как домен/аспект.
- **Смешанные запросы** — реализация контракта `ARCHITECTURE.md` §3.5: распознавание связующего маркера, объединение allow-list'ов, бюджет `min(Σ×0.8, HARD_CEILING 10 вызовов / 90с)`, запрещённые комбинации, фиксированный порядок `get_chart` → `draw_tarot`. Это **новая backend-логика**, а не адаптация существующей.

**Бот:** убрать клавиатуру выбора агентов (`app/bot/keyboards.py:212-218`) и жёсткие привязки `agent="chiromant"` (`features.py:65`), `agent="astro"` (`features.py:538`) — они должны идти через тот же intent.

**Приёмка:** ни один маршрут/экран не содержит выбора агента (инвентаризационный тест); смешанный вопрос «что скажут карты про мой Сатурн» использует и Таро, и натальную карту (тесты N-1, N-2, N-5, N-6); allow-list в однодоменовом режиме не даёт домену Таро вызвать `get_chart`; safety-тесты (CRISIS не доходит до LLM, лимит не списывается) зелёные.

**Порядок внутри этапа:** сначала однодоменовый Oracle (адаптация allow-list), затем смешанные запросы. Если смешанные запросы не успевают, этап закрывается без них — однодоменовый единый Oracle уже является ценностью, смешанные можно доделать после, не ломая контракт.

**Риски:**
- Слияние четырёх `SYSTEM.md` в один с доменными секциями — текстовый долг. Делать после рабочей механизмки, не до.
- Строгие валидаторы (`validate_chart_text`, `validate_tarot_text`) в free-chat не вызываются. Когда доменных границ не останется, это единственное покрытие соответствия ответа расчёту — подключить на этом этапе.

## Этап 6. Память с графом связей (две новые таблицы + три колонки)

**Что делаем:** аддитивная миграция. Существующие строки не удаляются и не мигрируются.

Детали модели — `ARCHITECTURE.md` §4. Принцип: `partners` остаётся таблицей людей; добавляются две таблицы и три колонки.

**Точный объём изменений схемы** (миграция `0016_memory_graph.py`):

| Что | Тип изменения | Назначение |
|---|---|---|
| `memory_links` | **CREATE TABLE** (новая) | Связи «факт ↔ человек / событие / разговор / расклад» |
| `personal_events` | **CREATE TABLE** (новая) | Личные события, сохранённые пользователем |
| `memories.source_kind` | **ADD COLUMN** | `user` или `derived` — разделяет факт и предположение |
| `memories.event_id` | **ADD COLUMN** | Связь факта с событием |
| `users.age_confirmed_at` | **ADD COLUMN** | Timestamp подтверждения 16+ (`ARCHITECTURE.md` §5.1) |
| 2 индекса на `memory_links` | **CREATE INDEX** | Поиск связей в обе стороны |
| 1 индекс на `personal_events` | **CREATE INDEX** | Хронология |

Все операции — `IF NOT EXISTS`, все новые колонки с `DEFAULT`, поэтому миграция применима к существующим данным без бэкфилла. Откат = drop двух таблиц и трёх колонок.

**Возрастная политика — НЕ ПРИМЕНЕНО (расхождение зафиксировано).** Ниже — исходное предложение этого плана; оно **противоречит текущему состоянию**:
- Предполагалось: новая колонка `users.age_confirmed_at`, `onboarding_complete` выставляется только вместе с ней.
- Фактически: возрастной гейт удалён миграцией `0006_drop_age_columns` (GAUNTLET v2) — колонок `age_confirmed`/`age_proof_hash` нет, в `ProfileIn` нет поля `age_confirmed`, `GET /api/me` не отдаёт `age_confirmed_at`. Проверено `PATCH {"age_confirmed": true}` → `200` с `updated: []`.
- Следствие: подтверждение 16+ существует **только** как обязательный клиентский шаг онбординга; серверного гейта нет. Восстановление серверной проверки — отдельное решение (юридическое + миграция), не часть этапа 4.1.

**Ограничение допустимых типов связей** (`memory_links`): `left_kind` и `right_kind` ∈ `{memory, partner, reading, diary, event}` — закрытый набор, валидируется приложением (в SQL без CHECK, чтобы не блокировать будущие типы). Связь человек↔человек допустима, связь факт↔факт запрещена.

**Обязательные требования (проверяемые):**
- Память включается осознанно (`memory_enabled`, default 0).
- Отключённая память не используется — проверка в инструментах (`tool_registry.py:937,950,960`).
- Просмотр, правка, удаление сохранённых данных.
- Полная изоляция между пользователями (owner-scope в SQL; параметра `tg_id` в контракте нет).
- Сохранённые события не смешиваются с AI-предположениями (разные маркеры в модели и в UI).
- Удаление аккаунта обрабатывает все связанные записи (`anonymize`, `app/repo/users.py:202` — жёсткий allowlist таблиц + обезличивание финансового следа). `memory_links` и `personal_events` добавляются в тот же allowlist, `age_confirmed_at` — в список обезличиваемых полей профиля.

**Приёмка:** consent-off блокирует запись (тест уже есть: `test_memory_tools_cannot_bypass_memory_off`); cross-user изоляция новой таблицы; `/api/account/delete` чистит граф; обратная совместимость — старые `memories` без связей читаются как «без привязки».
