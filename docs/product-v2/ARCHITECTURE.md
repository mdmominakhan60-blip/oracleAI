# OracleAI v2 — Architecture

Зафиксированная архитектура: что есть, что остаётся без изменений, что адаптируется и что проектируется. Все ссылки на файлы — относительно корня репозитория (рабочая копия `youthful-panini-634102`).

---

## 1. Принципы

1. **Один backend.** FastAPI, FastAPI-контракты, FastAPI-авторизация. Второй API и вторая база не создаются.
2. **Один фронтенд, раздаётся тем же origin.** Новая сборка идёт через тот же `GET /` и тот же `/static`.
3. **Расчёты — только сервер.** Клиент не считает планеты, карты, арканы и баллы.
4. **Модель объясняет, код считает.** Детерминированные инструменты как единственный источник фактов.
5. **Единый Oracle.** Пользователь не выбирает домен; домен выбирается по намерению.
6. **Память управляема.** Включение осознанное, удаление полное, изоляция абсолютная.
7. **Никаких статических моков.** Если функция не работает через реальный API — она не реализована.

## 3. Целевая архитектура v2

### 3.1 Frontend — `frontend-v2/`

| Слой | Ответственность | Технология |
|---|---|---|
| Точка входа | Инициализация Telegram SDK, миnt сессии, bootstrap `/api/me` | `@tma.js/sdk-react` + React 19 + TS |
| Роутинг | Hash-режим (`#/chat`, `#/people`, …) — решение зафиксировано в `MIGRATION_PLAN.md` Этап 4 | React Router |
| Состояние | Серверный кеш (bootstrap, chat, tarot) + локальное UI-состояние | TanStack Query или аналог |
| API-слой | Единственный клиент: авторизация, идемпотентность, ретраи, санитизация ошибок | Порт `miniapp/js/01-utils.js:43-177` |
| Дизайн-система | Токены R03 + компоненты | CSS custom properties + React |
| Сцены | `<TarotDeck>`, `<ChartWheel>`, `<PersonProfile>`, `<Timeline>` — визуальный опыт внутри диалога | React + SVG + CSS 3D |
| i18n | Единый словарь, ru/en, русский род отдельным слоем | Новый слой (в v1 6 разрозненных словарей) |

**Почему hash-режим:** SPA-fallback отсутствует. `GET /{filename}` (`app/api/main.py:398`) — catch-all на один сегмент, отсекающий `/`, `\` и ведущую `.` для защиты от `..%2F.env`. Прямые роуты (`/oracle`, `/chart`) вернут JSON 404. Hash не требует изменений в backend и не трогает защиту catch-all. Обработка `URL`-параметра (`?startapp=`), если понадобится, добавляется отдельным роутом.

### 3.2 Backend — контракты не меняются, поведение расширяется

**Каркас и контракты не переписываются.** Всё, что нужно v2, уже есть как механизм:

- `POST /api/chat/oracle` — единый вход (`API_CONTRACTS.md` §4).
- `GET /api/me` — bootstrap.
- 33 детерминированных инструмента.
- Owner-scope в SQL, лимиты, биллинг, safety.

**Аддитивные изменения backend (минимальные):**
| Изменение | Причина | Этап |
|---|---|---|
| `rate_limit` понимает `X-Session-Token` | Сейчас идентичность только из `x-init-data`/`dev_user`, иначе `ip:{host}` → под NAT общий лимит (`app/api/deps.py:75-88`) | 2 |
| Allow-list из intent, не из `spec.skills` | Единый Oracle: домен определяется вопросом | 5 |

Список endpoint'ов и payload'ов — `API_CONTRACTS.md`.

### 3.3 AI Orchestration — единый вход, скрытая маршрутизация

**Полный путь запроса:**

```
1. Пользователь печатает вопрос
      │  до 1000 символов, X-Idempotency-Key
      ▼
2. POST /api/chat/oracle {text}
      │
3. Авторизация: X-Session-Token → tg_id; fallback x-init-data → HMAC
      │  (невалидно → 401; нет в БД → 404; blocked → 403; deleted → 410)
      ▼
4. Валидация: pydantic AskIn, лимит длины, rate_limit bucket "llm" (12/60с)
      │
5. safety.classify(question)          ─── КРИЗИС ──▶ код собирает ответ,
      │                                          LLM не зовётся, лимит не тратится
      ▼
6. routing.route_agent(question)      ← ДЕТЕРМИНИРОВАННЫЙ РОУТЕР, без LLM
      │  scoring по доменам: chiromant / tarot / astro / oracle
      │  авто-роутинг: confidence ≥ 0.76 И отрыв от 2-го места ≥ 2
      │  (confidence — результат формулы 0.68 + 0.05·score + 0.04·отрыв, cap 0.98)
      │  два «жёстких» домена сразу → остаётся у Oracle, просит уточнить
      ▼
7. Лимиты: limits.user_lock(tg_id) → limits.check → entitlements.can_use
      │  списание СТРОГО до генерации; не хватило → ChatDenied (402/429)
      ▼
8. Память: recall_memory (consent-gated) + краткая история треда
      │  + shared_context за 30 дней (анти-контрадикция)
      ▼
9. LLM: _WorkflowBudget (timeout + tool_calls + cost_usd)
      │  allow-list инструментов = frozenset(домен)
      │  параллельные tool-calls, каждый с TOOL_TIMEOUT=15с
      │  fallback между провайдерами (anthropic → openai → custom)
      ▼
10. Каждый инструмент считает КОДОМ и возвращает данные + guide
      │  33 инструмента: карта, матрица, таро, совместимость, ведика, память…
      ▼
11. Проверка результата:
      │  validate_nonfatal_text — запрет «точно случится/гарантированно»
      │  слишком короткий ответ (<50 символов) → повторная генерация
      │  макс. 2 попытки с feedback
      ▼
12. Ответ: save_message + shared_context.record + analytics + product_cost
      │  фоновая extract_memory_llm (если память включена и не followup)
      ▼
13. Payload: answer, agent, routing, agent_profile, proof, thread_id, charge, allowance
```

**Что именно переносим из v1 без изменений:** шаги 3, 5, 6, 7, 8, 9, 10, 11, 12. Меняется только шаг 6→9: allow-list теперь вычисляется из домена вопроса, а не из выбранной персоны.

**Как сохраняются инварианты после удаления явного выбора:**

| Инвариант | Механизм v1 | Механизм v2 |
|---|---|---|
| Allow-list инструментов | `frozenset(spec.skills)` — из выбранной персоны | `frozenset(domain_tools[domain])` — из маршрутизированного домена. **Механизм тот же, источник меняется** |
| Домен Таро не считает натальную карту | У Таролога нет `get_chart` в `tools` | У домена `tarot` нет `get_chart`. Список доменных наборов наследуется из существующих `agent.yaml` (`tools:`) — данные не переписываются |
| Ограничения стоимости | `_WorkflowBudget` + per-agent `max_turns/max_tool_calls/timeout_s` | Бюджет тот же; per-agent лимиты становятся per-domain: `chiromant` сохраняет 20с / 4 / 6 и `risk_level: high` |
| Детерминированность | Инструменты считают кодом | Не меняется |
| Безопасность | Кризис на коде, safety-тайл последним в промпте | Не меняется |
| Анти-контрадикция | `shared_context` между агентами | То же, ключ меняется с `agent` на `domain` |

**Слияние промптов.** 4 файла `app/agents/<code>/SYSTEM.md` (Мира 48 строк, Урания 21, Ленорман 18, Лилит 17) — **DEFER**, не в этапе 5. Сначала механический единый Oracle с существующими `SYSTEM.md`, потом слияние в один с доменными секциями. Причина: слияние промптов без тестов на качество ответов — способ незаметно ухудшить продукт.

### 3.5 Контракт поведения: три случая запроса

**Текущий роутер однодоменовый.** Это зафиксированный факт, а не предположение: `route_agent()` возвращает **одного** победителя (`return RouteDecision(winner, ...)`), и при двух «жёстких» доменах (score ≥3 у двух и более) намеренно остаётся у Oracle с `reason = "ambiguous hard domains; ask a clarifying question"` (`routing.py:105-107`). Смешанный запрос в v1 **не работает**. Ниже — контракт, который это исправляет.

#### Случай 1. Один домен

```
route_agent() → один домен D с confidence ≥ 0.76 и отрывом ≥ 2
allowed_tools = domain_tools[D]
бюджет        = budget[D]
```
Поведение идентично текущему. Изменений не требуется.

#### Случай 2. Смешанный запрос (несколько доменов)

Пример: «что скажут карты про мой Сатурн в этом месяце» → Таро + астрология.

**Распознавание.** Два условия, оба обязательны:
1. Роутер вернул `ambiguous hard domains` (score ≥3 у двух и более доменов);
2. Вопрос содержит **связующий маркер**: союз или предлог, требующий обоих результатов («про», «по», «и», «вместе с», «учитывая», «согласуется ли с»).

Если маркера нет — это **не смешанный запрос, а неопределённость** (случай 3). Одно перечисление двух тем («Таро и карта») без связки не делает запрос смешанным: модель не знает, что именно согласовать.

**Выбор инструментов.**
```
primary_domain   = домен с максимальным score (ranked[0])
secondary_domains = остальные домены со score ≥ 3

allowed_tools = domain_tools[primary_domain]
             ∪ ⋃ domain_tools[d] for d in secondary_domains
             − FORBIDDEN_IN_COMBINATION
```
То есть **объединение** allow-list'ов. Инвариант «Таро не считает натальную карту» **сохраняется**, но меняет природу: он перестаёт быть постоянным свойством домена и становится запретом на конкретную комбинацию.

`FORBIDDEN_IN_COMBINATION` — пары, запрещённые **к параллельному выполнению** в рамках одного хода LLM:
| Пара | Почему параллельность запрещена |
|---|---|
| `draw_tarot` + `get_chart` / `get_transits` / `get_all_placements` | Композер не должен получать и карты, и точный расчёт одновременно: интерпретация заканчивается на том, что вернулось первым, и вторая половина не используется либо подменяет первую. **Последовательный вызов разрешён** — см. порядок ниже |
| `palm_*` + любой другой домен | Требует загрузки фото (`POST /api/palm`); в текстовом ходу выполнимо только как предложение прислать фото, инструменты других доменов при этом не вызываются |

**Допустимый порядок для «Таро + астрология».** Последовательное выполнение — норма, запрещена только параллельность:
```
1. get_chart / get_transits / get_all_placements   ← детерминированный расчёт
2. (модель читает результат, формирует вопрос к картам)
3. draw_tarot                                       ← карты, уже под расчёт
```
Почему именно так, а не наоборот: карты тянутся один раз и сохраняются (`immutable_cards`, `tarot.py:383`), и их трактовка должна опираться на **уже известный** расчёт. Если тянуть карты первыми, модель интерпретирует их в отрыве от карты пользователя, и связка «аркан ↔ положение» получается декоративной.

Технически порядок выражается ограничением allow-list'а **на ход**, а не на ответ:
```
ход 1: allowed = domain_tools[astro]                    (карт нет в allow-list)
ход 2+: allowed = domain_tools[astro] ∪ domain_tools[tarot]
```
Первая итерация цикла видит только расчётные инструменты; `draw_tarot` становится доступной после того, как расчёт уже в контексте. Это реализуется фильтром инструментов по номеру итерации в `run_agent` — та же механика, что существующий `max_iters`/`_WorkflowBudget`.

**Бюджет.** Смешанный запрос дороже однодоменового, поэтому:
```
budget[combined] = min(
    _WorkflowBudget по настройкам (timeout + tool_calls + cost_usd),
    sum(budget[d] for d in involved_domains) × 0.8,   # 20% скидка на накладные расходы
    HARD_CEILING                                      # абсолютный потолок
)
```
`HARD_CEILING` = **10 вызовов инструментов и 90с** (существующие `llm_max_tool_calls=12` / `llm_workflow_timeout=90` из `app/config.py`). Скидка 20% нужна, чтобы смешанный запрос не стоил как два отдельных: расчёты разделяют один системный промпт и один контекст.

**Ограничения безопасности.** Не ослабляются ни при какой комбинации:
- Кризисный путь (`safety.CRISIS`) проверяется **до** роутинга — смешанный запрос в кризисе обрабатывается как кризис, а не как комбинация доменов.
- `risk_level` = максимум по всем вовлечённым доменам. Если задействован `chiromant` — уровень `high` для всего ответа.
- `validate_nonfatal_text` применяется к итоговому ответу целиком, а не пофрагментно.
- Таймлимит `chiromant` (20с) не заменяется суммой: при его участии применяется **наиболее строгий** из лимитов.

**Что видит пользователь.** Один ответ, один собеседник, один разговор. Пользователь остаётся на вкладке Oracle. Ответ содержит **все** затребованные части; `proof.tools_used` перечисляет фактически использованные инструменты. Никакого «спросила Уранию и Ленорман» — допустима только мягкая маркировка по инструментам («посмотрела карту и вытянула карты»).

**Критерии тестирования** (`ACCEPTANCE_CRITERIA.md` A5-3, `TEST_PLAN.md` N-1/N-2/N-7):
- «что скажут карты про мой Сатурн» → `proof.tools_used` содержит инструменты **и** Таро, **и** астрологии.
- В ответе оба фрагмента присутствуют, один из них не вытеснен.
- `get_chart` вызван **раньше** `draw_tarot` (проверка порядка в `tools_used`).
- `draw_tarot` **не** вызван в первой итерации цикла (проверка, что параллельность не произошла).
- Бюджет не превышен: ≤10 вызовов, ≤90с.
- `palm_*` + другой домен → инструменты другого домена не вызываются, ответ предлагает прислать фото.

#### Случай 3. Неоднозначность

```
route_agent() → ambiguous hard domains БЕЗ связующего маркера
              ИЛИ winner == DEFAULT_AGENT при score == 0
              ИЛИ отрыв от 2-го места < 2
allowed_tools = domain_tools["oracle"]     # только разговорный домен
```
Oracle **не угадывает** домен и не вызывает уточняющие инструменты. Он отвечает как собеседник и задаёт **один** конкретный вопрос: «Тебе ближе посмотреть в карту или вытянуть карты?»

Почему один вопрос, а не список: два вопроса подряд — это форма, а не разговор.

**Критерии тестирования:** `routing.reason` содержит уточнение; `tools_used` не содержит доменных инструментов; ответ содержит ровно один уточняющий вопрос.

#### Сводка

| Признак | Домен | Инструменты | Бюджет |
|---|---|---|---|
| Явный один домен | `ranked[0]` | `domain_tools[D]` | `budget[D]` |
| Два+ домена + связующий маркер | primary + secondary | объединение минус запреты | min(budget, Σ×0.8, HARD_CEILING) |
| Неоднозначно | `oracle` | только разговорные | `budget[oracle]` |

## 4. Память: проектирование графа связей

### 4.1 Что есть сейчас (факт)

```
memories(id, tg_id, fact, kind, weight, embedding, embed_model, last_used, created_at)
   kind ∈ person|event|emotion|goal|fact      ← единственная категоризация
   факт = ОДНА строка текста
   СВЯЗЕЙ НЕТ: ни с людьми, ни с событиями, ни с раскладами, ни с дневником

partners(id, tg_id, name, relation, birth_date, birth_time, birth_city,
         birth_lat, birth_lon, tz, chart_json, created_at)
   люди живут отдельно, в memories о них нет ссылки

tarot_readings(id, tg_id, spread, question, cards_json, …, deck, created_at)
   нет person_id, нет ссылки на событие

diary(id, tg_id, text, mood, created_at)
   нет ни одной ссылки
```

`memories_full()` (`app/repo/dialog.py:420`) отдаёт плоский список. `kind="person"` — строка «моего парня зовут Дима», но `partners.id=7` из неё не извлечь. Поэтому UI «связать человека с фактом» невозможно без нового слоя.

Проверено, что безопасно выразить существующими моделями: **ничего.** Отношения «факт ↔ человек», «расклад ↔ человек», «событие ↔ человек» в текущей схеме невыразимы. `GET /api/history` отдаёт только метаданные и не связывает сущности между собой.

### 4.2 Решение: минимальные аддитивные изменения

**Не создавать новую БД и не переписывать существующие таблицы.** Добавляем **две** новые таблицы (`memory_links`, `personal_events`), **две** колонки в `memories` (`source_kind`, `event_id`) и **одну** в `users` (`age_confirmed_at`) плюс 3 индекса. Все операции обратимые `IF NOT EXISTS` / `ADD COLUMN IF NOT EXISTS` в новой миграции.

**Новая миграция `0016_memory_graph.py`:**

```sql
-- Связи «что угодно ↔ что угодно». Одна строка = одно ребро.
CREATE TABLE IF NOT EXISTS memory_links (
    id          BIGSERIAL PRIMARY KEY,
    tg_id       BIGINT NOT NULL,
    -- "что" и "с чем": kind + id этой сущности. Никаких FK — см. ниже.
    left_kind   TEXT NOT NULL,     -- memory | partner | reading | diary | event | thread
    left_id     BIGINT NOT NULL,
    right_kind  TEXT NOT NULL,
    right_id    BIGINT NOT NULL,
    -- как эта связь возникла: explicit → пользователь связал вручную;
    -- derived → система связала по эвристике и помечает это как наблюдение
    origin      TEXT NOT NULL DEFAULT 'explicit',  -- explicit | derived
    created_at  TEXT
);
CREATE INDEX IF NOT EXISTS idx_memory_links_tg_left
    ON memory_links (tg_id, left_kind, left_id);
CREATE INDEX IF NOT EXISTS idx_memory_links_tg_right
    ON memory_links (tg_id, right_kind, right_id);

-- Личные события: это сохранённое, не AI-предположение.
CREATE TABLE IF NOT EXISTS personal_events (
    id          BIGSERIAL PRIMARY KEY,
    tg_id       BIGINT NOT NULL,
    title       TEXT NOT NULL,
    happened_on TEXT,              -- YYYY-MM-DD, опционально
    note        TEXT,
    source_kind TEXT NOT NULL DEFAULT 'user',  -- user | diary | reading
    source_id   BIGINT,
    created_at  TEXT
);
CREATE INDEX IF NOT EXISTS idx_personal_events_tg
    ON personal_events (tg_id, happened_on);

-- Разделяем сохранённое и предположенное на уровне модели
ALTER TABLE memories ADD COLUMN IF NOT EXISTS source_kind TEXT NOT NULL DEFAULT 'user';
-- user   → пользователь сказал / написал сам
-- derived → система связала сама, это наблюдение, не факт
ALTER TABLE memories ADD COLUMN IF NOT EXISTS event_id BIGINT;
```

**Почему без `FOREIGN KEY`:** цели связей лежат в разных таблицах разной формы. Составной FK тут даст хрупкость без пользы; вместо него приложение поддерживает инвариант, а `origin='explicit'|'derived'` разделяет «пользователь сказал» и «система связала».

**Про `thread` в типах связей.** `SCREEN_SPEC.md` §8 и `UX_FLOWS.md` §5.2 обещают блок «Разговоры» (о чём говорили с этим человеком). Чтобы обещание стало функцией, в `left_kind`/`right_kind` добавляется шестой тип — `thread` (ссылка на `threads.id`, существующая таблица).

Ограничения, чтобы `thread` не создал утечки:
- Связь `thread ↔ partner` — **только `origin='derived'`**: система создаёт её по совпадению имени человека в текстах треда. Пользователь может такую связь удалить, но не создать вручную — вручную он связывает не тред, а отдельный факт.
- `GET /api/people/{id}/timeline` для `kind=thread` отдаёт **только метаданные**: `id`, `title`, `created_at`, `preview=""` — как в существующем `/api/history`, где для чатов `preview` принудительно пустой (`history.py`). Приватный текст переписки из таймлайна Relationships недоступен.
- `GET /api/people/{id}` аналогично: блок `conversations` содержит `{id, title, created_at, messages_count}` без текста сообщений.

Если на MVP решают отказаться от блока «Разговоры», он удаляется из обоих экранов, тип `thread` остаётся в схеме неиспользуемым — удаление колонки дешевле, чем её добавление потом.

**Совместимость:** все добавления — `IF NOT EXISTS`, значения по умолчанию (`'user'`). Существующие `memories` без `source_kind` получают `'user'` — корректно: они извлечены из слов пользователя. Существующие строки `partners`, `tarot_readings`, `diary` не трогаются. Откат = drop новых таблиц и трёх колонок. `users.age_confirmed_at` у существующих пользователей остаётся `NULL` — они не подтверждали возраст явно, и гейт предложит им сделать это при первом входе.

**Расширение `anonymize`** (`app/repo/users.py:202`): добавить `memory_links`, `personal_events` в существующий allowlist из 19 таблиц. Там уже есть инвариант «keep the table names static so dynamic SQL cannot be injected» — просто расширяем кортеж, ничего не меняя в механизме.

### 4.3 Новые endpoint'ы (единственные новые в v2)

**13 endpoint'ов**, точные контракты с request/response/ошибками — `API_CONTRACTS.md` §11–11.2. Сводка:

| Группа | Пути |
|---|---|
| Люди | `GET /api/people`, `POST /api/people`, `GET /api/people/{id}`, `DELETE /api/people/{id}` |
| События | `GET /api/events`, `POST /api/events`, `GET /api/events/{id}`, `DELETE /api/events/{id}` |
| Факты | `GET /api/memories/{id}`, `PATCH /api/memories/{id}` |
| Связи | `POST /api/memory-links`, `DELETE /api/memory-links/{id}` |
| История | `GET /api/people/{id}/timeline` |

Все с `Depends(current_user)`, owner-scope `WHERE ... AND tg_id=:tg_id` в SQL, rate-limit bucket `read`/`write`. Параметра `tg_id` в контракте нет ни у одного.

Ключевые ограничения (полный список — в `API_CONTRACTS.md`):
- `memory_links` с типом `thread` — только `origin="derived"`, создаётся сервером;
- `source_kind` и `age_confirmed` через `PATCH` не устанавливаются клиентом;
- Timeline и карточка человека отдают для разговоров **только метаданные**, `preview=""` — приватный текст переписки не отдаётся, как в `/api/history`;
- Удаление связей — приложением, не `ON DELETE CASCADE`: одна ошибка схемы не должна утаскивать факты.

### 4.4 Consent и изоляция

**Consent (тройная проверка, не меняется):**
1. В API: `GET /api/memories` возвращает `[]` при `memory_enabled=0` (`profile.py:444`); `POST /api/memories` → 409 (`profile.py:457`).
2. В контексте: `runtime.py:70-72` подставляет только shared-context при выключенной памяти.
3. **В самих инструментах:** `save_memory` (`tool_registry.py:937`), `recall_memory` (`:950`), `recall_diary` (`:960`) — первая строка каждого: `if not bool(user["memory_enabled"]): return "память выключена…"`. Комментарий в коде формулирует инвариант: «Tool calls are model-generated and must never be able to override the user's setting».

**Новое для графа:** `memory_links` и `personal_events` — тоже под consent. При `memory_enabled=0` новые связи не создаются, существующие читаются как read-only (пользователь имеет право **увидеть**, что запомнено, даже выключив память — иначе удаление становится невозможным).

**Изоляция:** параметра `tg_id` нет ни в одном контракте; owner-scope в SQL. Тестируется кросс-юзером (`TEST_PLAN.md`).

### 4.5 Сохранённое ≠ предположенное

Требование продукта: «сохранённые события не смешиваются с AI-предположениями».

| Тип | Маркер | Пример |
|---|---|---|
| Факт (сохранённое) | `source_kind='user'` | «моего парня зовут Кирилл» |
| Наблюдение (предположение) | `source_kind='derived'`, `origin='derived'` | «по трём раскладам ты возвращаешься к теме контроля» |

В UI разные визуальные маркеры (`UX_FLOWS.md` §6). Модель **не имеет права** писать `source_kind='user'` — это значение по умолчанию только для путей, где источник — слова пользователя (`extract_memory_llm` с диалога, дневник, ручное создание).

| Вопрос | Текущее состояние | Рекомендация |

### 5.1 Возрастная политика и приватность

**Текущее состояние (факт, не предположение).** Возрастная проверка **удалена из системы**. Миграция `0006_drop_age_columns` убрала колонки `age_confirmed` и `age_proof_hash`, а `confirmed_age_user` в `app/api/deps.py:161-167` теперь — алиас `current_user` с docstring «возрастной гейт полностью удалён». То есть на данный момент **сервер не проверяет возраст вообще**.

**Чего клиентский флажок не делает.** Один чекбокс в онбординге не обеспечивает соблюдение возрастной политики: он не верифицирует, не сохраняется в проверяемом виде и не защищает от прямых вызовов API. Он документирует намерение, но не является контролем.

**Зафиксированное решение для v2:**

| Уровень | Что делаем | Что это даёт |
|---|---|---|
| Онбординг | Явное подтверждение «мне 16+» — обязательный шаг, без него `onboarding_complete` не выставляется | Осознанное согласие пользователя |
| Профиль | Новое поле `age_confirmed_at` (timestamp подтверждения) | Проверяемый след, когда согласие дано |
| Сервер | `age_confirmed_at IS NOT NULL` требуется для `active_user` (платный контент: `/api/today`, `/api/compat/full`, `/api/synastry`, `/api/composite`, `/api/transits`, `/api/returns`, `/api/chart/pdf`) | Платный контент недоступен без подтверждения |
| Сервер | Read-эндпоинты **не** гейтируются возрастом | Не ломаем существующих пользователей, зарегистрированных до введения гейта |

**Почему только `active_user`, а не все ручки:** гейт на всех ломал бы обратную совместимость для уже зарегистрированных пользователей. Платный контент — точка, где юридический риск реален и где гейт можно ввести без миграции данных.

**Соответствие остальным требованиям:**
- **Telegram-авторификация** — не меняется: initData HMAC + сессии. Подтверждение возраста привязывается к `tg_id`, подделать личность нельзя.
- **Consent памяти** — остаётся тройным (API, контекст, сами инструменты). Подтверждение возраста не связано с consent'ом памяти: разные решения, независимые поля.
- **Изоляция пользователей** — не меняется: owner-scope в SQL, параметра `tg_id` в контракте нет.
- **Экспорт** — `GET /api/account/export` дополнительно отдаёт `age_confirmed_at` как часть профиля.
- **Удаление** — `anonymize` (`app/repo/users.py:202`) уже обезличивает профиль; `age_confirmed_at` должен быть в списке обезличиваемых полей (добавляется в тот же allowlist-механизм, что и колонки графа памяти).

**ОТКРЫТЫЙ ЮРИДИЧЕСКИЙ ВОПРОС (не закрыт спецификацией).** Достаточно ли самопровозглашения «мне 16+» для целевых юрисдикций, или требуется верифицируемое подтверждение возраста (как это делают продукты с контентом 18+), — решает юрист, а не инженер. Кроме того:

- Не определены целевые юрисдикции и применимые к ним требования (COPPA 13+ в США, GDPR-K в ЕС, возрастные рамки РФ).
- Privacy Policy и Terms в репозитории — заглушки: оператор, контакты, юрисдикция не заполнены.
- Категория продукта (эзотерика/развлечение vs. псевдо-медицина) влияет на требования к дисклеймерам; кризисный протокол есть, но его правового статуса никто не оценивал.

**Эти вопросы не блокируют разработку** Этапов 1–5, но должны быть закрыты до публичного релиска. Инженерная часть (поле, шаг онбординга, гейт на `active_user`) реализуема независимо от юридического решения.
