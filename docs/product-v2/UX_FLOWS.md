# OracleAI v2 — UX Flows

Сценарии пользователя. Каждый поток описывает: цель, шаги, решения, состояния и точки отказа. Конкретные API и payload'ы — в `API_CONTRACTS.md`, детали экранов — в `SCREEN_SPEC.md`.

---

## 0. Принципы навигации

1. **Четыре нижние вкладки.** Home · Oracle · People · Me. Это весь способ перемещения по продукту. Не лабиринт разделов, не сетка иконок.
2. **Oracle — единый чат.** Пользователь говорит обычным языком и не выбирает, «кто будет отвечать».
3. **Home — это не чат.** Персональная сводка дня с быстрыми действиями. Чат живёт на своей вкладке.
4. **Инструменты проявляются в диалоге.** Таро, карта, память — это сцены внутри разговора, а не отдельные приложения.
5. **Лист и диалог предпочтительнее страницы.** Если содержимое решает одну задачу и занимает меньше одного экрана по высоте, это bottom sheet или inline-блок, а не маршрут.
6. **Мобильный first.** Одной рукой, в вебвью Telegram, с учётом safe-area и клавиатуры.

### Иерархия маршрутов v2

Нижние вкладки — 4, остальное внутри них.

```
/                    [вкладка 1] HOME — персональная сводка и быстрые действия
/oracle              [вкладка 2] ORACLE — единый чат со скрытой маршрутизацией
/people              [вкладка 3] PEOPLE — карточки людей и история отношений
/people/:personId    карточка человека (маршрут внутри вкладки, не таб)
/people/:id/timeline обратная хроника по линии отношений
/settings            [вкладка 4] ME — профиль, тон, память, экспорт, удаление
/memory              паттерны и управляемая память (вход из ME и из Oracle, не таб)
/chart               натальная карта: визуальный сценарий, не нижняя вкладка
/reading/:id         сохранённый расклад Таро (вход из истории, не таб)
```

Почему именно так:

- **Home и Oracle разделены.** Home отвечает «что сейчас со мной и что можно сделать»; Oracle отвечает «поговорить». Слияние этих задач в один экран даёт интерфейс, где либо сводка мешает диалогу, либо диалог мешает сводке.
- **Натальная карта и Таро — не вкладки.** Это визуальные сцены: карта открывается из Home/Oracle, Таро — внутри диалога. Четыре вкладки сохраняются стабильными, а тяжёлые визуализации не миксуются с навигацией.
- **`/memory` — не вкладка** доступен из ME и из ответа Oracle, но не занимает постоянное место в навигации: память — это то, что управляют эпизодически, а не то, куда заходят каждый день.

Важно: **SPA-fallback сейчас отсутствует.** `GET /{filename}` в `app/api/main.py:398` — catch-all на один сегмент, и `/oracle` вернёт JSON 404. Это блокирует глубинке ссылки; решение зафиксировано в `MIGRATION_PLAN.md` Этап 4 (hash-режим роутера или явные роуты).

## 1. Первый вход и возвращение

**Цель:** новый пользователь за 3–4 шага получает персональный результат; вернувшийся — сразу Home. Он ещё не платил, поэтому первый инсайт обязан быть реальным.

### Развилка после bootstrap

Единственная точка решения — ответ `GET /api/me`. Условие читается один раз, при старте:

```
[Открыл из Telegram]
        │
        ▼
  POST /api/auth/session  {init_data}
        │  401 → renderAuthRequired «Открой из Telegram»
        ▼
  GET /api/me            ← bootstrap, единственный источник развилки
        │
        ├── me.onboarded === true ─────────▶ [Home, вкладка 1]
        │                                     (Welcome, Onboarding, First Insight
        │                                      НЕ показываются)
        │
        └── me.onboarded === false ────▶ [1. WELCOME]
                                              │ продолжить (1 тап)
                                              ▼
                                       [2. ONBOARDING]
                                              │
                          ┌───────────────────┼────────────────────┐
                          ▼                   ▼                    ▼
                    [3. BIRTH           [3b. BIRTH           [3c. TONE]
                     дата/время/        no time]             образ Oracle
                     город]                                   (friend/witch/mentor)
                          └───────────────────┴────────────────────┘
                                              │
                                    PATCH /api/profile {onboarding_complete:true}
                                              ▼
                                     [4. FIRST INSIGHT]
                               «Вот что я вижу в твоей карте»
                                              │
                                     задать вопрос
                                              ▼
                                     [Home, вкладка 1]
```

**Точные условия переходов:**

| Состояние | Условие | Куда |
|---|---|---|
| Не авторизован | `POST /api/auth/session` → 401 | Экран «Открой OracleAI из Telegram» + повтор |
| Новый пользователь | `me.onboarded === false` | Welcome → Onboarding → First Insight → Home |
| Onboarding начат, не завершён | `me.onboarded === false`, `me.onboarding_step !== null` | **Середина онбординга**, на шаге `onboarding_step` — не с начала |
| Вернулся после онбординга | `me.onboarded === true` | **Сразу Home**. Welcome / Onboarding / First Insight не показываются никогда |
| Вернулся, есть переписка | `me.onboarded === true` | Home. История чата остаётся прежней |
| Анонимизирован | `GET /api/me` → 410 | Экран «Аккаунт удалён» + создание нового через бота |

**Вкладка Oracle — не подмена Home.** Первый вход заканчивается на Home, а **не** на чате: Oracle открывается пользователем (таб или кнопка «Спросить Oracle»), либо когда он сам задаёт вопрос. Автопереход в чат после онбординга сбивает точку входа — человек ещё не выбрал, куда идти.

**Сохранение промежуточного состояния.**
- Каждый шаг онбординга отправляет `PATCH /api/profile` с `onboarding_step` сразу после перехода, а не в конце. Прерванный на середине онбординг возобновляется с того же шага.
- Ответы на шаги (тема, дата, город, образ) сохраняются в профиле, а не в локальном state: смена устройства не теряет прогресс.
- «Пропустить» фиксирует шаг как пройденный с пустым значением — вежливо, но не блокирует прогресс (кроме шага 16+).

**Успешный bootstrap не сбрасывает историю диалога.**
`GET /api/me` вызывается один раз при старте и только для чтения: он не создаёт и не архивирует треды. Отдельно:
- повторный `GET /api/me` при возврате на Home и на вкладку Oracle не перезапрашивает историю — сообщения берутся из `GET /api/chat/oracle` или кеша;
- Onboarding не показывается повторно по условию `me.onboarded`; First Insight — не отдельное состояние, а первое сообщение в треде;
- сбой bootstrap → чат рендерится из кеша, онбординг не переспрашивается.
                          + 1 понятный факт + 1 вопрос
                                        │
                                   задать вопрос
                                        ▼
                                  [5. CHAT]
                            ┌─ первый ответ с памятью ─┐
                            └──────────────────────────┘
```

### Шаг 1 — Welcome
Цель: за 8 секунд объяснить, что это один Oracle, который помнит. Не экран-загрузка, не карусель из пяти картинок.

Структура: один сильный заголовок, одна фраза про память, одна кнопка. Фон — космос R03. Никаких форм.

### Шаг 2 — Onboarding
Здесь происходит продуктовое решение: **не спрашивать intent из четырёх агентов** (как сейчас в `miniapp/js/18-onboarding.js`). Вместо этого — один вопрос: «Что свелось тебе тяжелее всего в последнее время?» со свободным вводом и 3–4 подсказками (отношения, решение, усталость, тревога).

Это первое сообщение пользователя Oracle. Оно же становится контекстом первого ответа.

Кнопка «Пропустить» всегда доступна и не блокирует прогресс: онбординг не должен становиться paywall'ом перед ценностью.

### Шаг 3 — Birth Profile
Три состояния в зависимости от знания времени:

- **Знаю дату и время** → запрашиваем дату, время, город (`GET /api/city/suggest` для автодополнения). Полная карта с домами и асцендентом.
- **Знаю только дату** → честно говорим: без времени рождения карта читается по знакам и стихиям, без домов и асцендента. Это не «деградация», а корректный режим (`birth_time_precision: "approx" | "unknown"`, `chart_precision: "sun_only"`).
- **Не хочу говорить** → пропуск. Первый инсайт строится на Таро и разговоре, не на карте.

Валидация даты/города на клиенте и сервере; ошибка города → «не нашла такой город, попробуй иначе» без потери введённых данных.

### Шаг 4 — First Insight
Первый настоящий результат. Не приветствие, не заглушка.

- Если есть карта: `GET /api/matrix` + `GET /api/chart` → один сильный аркан Матрицы и один понятный аспект личности (не простыня из 20 пунктов).
- Если карты нет: короткий Таро-опросник → `POST /api/tarot/draw?spread=one` → одна карта + одна фраза трактовки (`POST /api/tarot/interpret/{id}`).

Обязательно: одна конкретная вещь + один вопрос обратно. Цель — начать разговор, а не выгрузить прогноз.

### Точки отказа
| Ситуация | Поведение |
|---|---|
| `POST /api/auth/session` → 401 | renderAuthRequired: «Открой OracleAI из Telegram» + кнопка повтора |
| `GET /api/me` → 5xx | Экран с нейтральным текстом и «Попробовать снова»; без стектрейсов |
| Город не найден | Инлайн-ошибка под полем, введённое не теряется |
| Нет сети | Офлайн-состояние: объяснение + повтор, черновик вопроса сохраняется |
| Кризисный текст в первом вопросе | safety-протокол отвечает кодом, до агента вопрос не доходит, лимит не тратится |

## 2. Home — персональная сводка (вкладка 1)

**Цель:** ответить на вопрос «что сейчас со мной и чем я могу заняться прямо сейчас». Это не чат и не дашборд с плитками: экран собирает ровно то, что персонально, и даёт быстрые действия.

**Данные:** `GET /api/me`, `GET /api/today`, `GET /api/moon/week`.

### Структура сверху вниз

1. **Приветствие по имени** + «ты была здесь N дней назад» (из `global_streak`, `diary_streak`).
2. **Карта дня** — одна карта Таро (`today.card`), с возможностью перевернуть и получить короткую трактовку. Не расклад — один аркан.
3. **Лунный ориентир** — фаза, лунный день, одна фраза совета (`today.moon`, `moon/week`).
4. **Что Oracle помнит сейчас** — 2–3 релевантных факта (`me.memories`) + ссылка в `/memory`. Не весь список: именно выжимка.
5. **Быстрые действия** — крупные кнопки:
   - «Спросить Oracle» → вкладка `/oracle`;
   - «Вытянуть карты» → `/oracle` с предзаполненным запросом (сценарий — внутри диалога, `SCREEN_SPEC` §10–11);
   - «Моя карта» → `/chart`;
   - «Люди» → вкладка `/people`.
6. **Следующий шаг** (`today.next_action`) — серверная рекомендация: нет карты → «Собрать карту», нет партнёров → «Совместимость», нет раскладов → «Расклад».

### Ключевое правило
Home не дублирует чат. Он не показывает ленту диалога — он показывает **состояние**: день, память, быстрый вход. Если пользователь хочет говорить, он идёт на вкладку Oracle.

### Состояния
| Состояние | Вид |
|---|---|
| Загрузка | Скелетон карточки дня + скелетон списка |
| Ошибка | Нейтральный текст + повтор; остальной контент, который загрузился, сохраняется |
| Пусто (новый пользователь) | Не пустой экран, а «Начнём?» → переход в онбординг или первый вопрос |
| Нет подписки (`active_user` 402) | Сводка работает, `/api/today` частично деградирует — показываем то, что доступно, без пустого экрана |

### Переходы
- В таб «Oracle» → `/oracle`
- «Вытянуть карты» → `/oracle` (диалог, не отдельная страница)
- «Моя карта» → `/chart`
- В таб «People» → `/people`
- Тап по факту памяти → `/memory`

## 3. Oracle — единый чат (вкладка 2)

**Цель:** главный разговорный экран продукта. Пользователь открывает и говорит. Всё остальное — через диалог.

### Поток

```
[Вкладка «Oracle»]  ── из Home или напрямую
        │
        ▼
   GET /api/me  (один раз, bootstrap; на Home уже загружено — кеш переиспользуется)
        │
        ├─ feedback_pending → мягкий баннер day7-опроса
        ├─ allowance.left == 0 и нет подписки → мягкий маркер «вопросы на сегодня исчерпаны»
        ▼
[6. ORACLE CHAT]  ◀── вторая нижняя вкладка, постоянный адрес
        │
   пользователь печатает вопрос
        │
        ▼
POST /api/chat/oracle {text}   (X-Idempotency-Key)
        │  НЕ /api/ask: та compat-ручка теряет routing/proof/thread_id
        │
        ├── 429 → «Слишком часто», Retry-After
        ├── CRISIS → ответ поддержки, лимит НЕ списан
        ├── лимит → [14. PAYWALL]
        ▼
   Oracle отвечает
        │
   ответ содержит routing.agent + proof.tools_used
        │
        ├── tarot   → показать сцену карт (см. поток 4)
        ├── chart   → показать сцену карты (см. поток 6)
        └── memory  → показать «я помню…» блок с ссылкой на /memory
        │
        ▼
   followup в тот же день → без списания (limits.FOLLOWUP, max 2)
```

### Ключевое UX-решение: домен не озвучивается
Старый фронт при авто-роутинге сам переключал `chat.key` и писал «Передала вопрос Урании» (`miniapp/js/07-chat.js:856-859`). В v2 этого нет: пользователь остаётся в одном чате. domain-driven сцена (карты/карта) появляется **внутри ответа** как визуальный блок, без смены собеседника.

Допустимая мягкая маркировка вместо «передала другому агенту»: подпись вроде «✨ посмотрела в карту» / «🎴 вытянула карты» — по `proof.tools_used`, не по имени персоны.

### Состояния
- **Загрузка:** не спиннер, а «фазы» — таймерные подписи более мягкой формы, чем «печатает» (старый механизм `STAGE_PHASES` переносится как «Oracle думает…»). Ответ приходит одним куском: **стриминга к клиенту нет ни в API, ни в старом фронте.**
- **Пусто:** не «начните диалог», а одна живая подсказка + 3 сценария-стартера, релевантных пользователю.
- **Ошибка:** нейтральный текст + «Попробовать снова»; вопрос сохраняется в черновике, не теряется.
- **Отмена:** `AbortController` — пузырь вопроса не остаётся, текст уходит в черновик.
- **Успех:** ответ + доказательная подпись (какие инструменты использованы) — это НЕ отладочная информация, а элемент доверия.

### Followup-правило
`limits.FOLLOWUP_MAX = 2`. Уточнение в пределах короткого окна не списывает вопрос. Пользователю это показывается как «уточнения не тратят лимит», не как скрытая механика.

## 4. Таро: выбор расклада и результат

**Цель:** Таро — эмоциональный центр продукта. Не форма с радио-кнопками, а колода, которую тасуют.

### 4.1 Триггер
Пользователь спрашивает «вытяни карты», «что выпадет», «расклад на отношения». Определить «хочет Таро» можно ДО платного draw по ключевым словам (тот же `routing._TERMS.tarot`), но решение всегда подтверждается человеком: колода не тсуется без явного «тянем».

### 4.2 Поток

```
[Oracle: «Хочешь, вытяну карты?»]
        │
   GET /api/tarot/spreads/full   (code, title, positions, tier, emoji, hint, guide)
        │
        ▼
[10. TAROT SPREAD SELECTOR]
   витрина: входит в тариф / куплено / стоит
        │
   выбрал расклад → спросили вопрос (обязателен)
        │
        ▼
POST /api/tarot/draw?spread=<code>   {question, deck}
        │
        ├── ChatDenied → [14. PAYWALL] «этот расклад премиум»
        ▼
{reading_id, title, positions, cards[], ledger, guide, deck, thread_id}
        │
        ▼
[11. TAROT READING RESULT]
   ┌─ раздача dealIn, стаггер 80мс ──────────────────┐
   │  N карт рубашкой вверх, позиции подписаны      │
   └─────────────────────────────────────────────────┘
        │
   пользователь открывает по порядку (1-й → 2-й → N)
        │  каждая: 130мс приподнимание → 550мс rotateY(180)
        │  следующая карта «дышит» (tarotNextCard 1.8s)
        ▼
   все открыты → кнопка «Что это значит»
        │
        ▼
POST /api/tarot/interpret/{reading_id}   (llm, лимит)
        │
        ▼
   трактовка + 1 конкретный шаг
        │
   опционально: POST /api/tarot/outcome/{id} {outcome: came_true|partly|no}
```

### 4.3 Почему draw и interpret — два запроса
Это не техническое неудобство, а намеренный контракт: `chat_svc.draw` сохраняет карты в БД **до** трактовки, «чтобы интерфейс успел показать анимацию переворота. Карты уже лежат в БД, подменить их нельзя» (`app/services/chat.py:305-307`). Контракт `TAROT_REPLAY_CONTRACT = {mode: "immutable_cards"}`.

Следствие для UX: переворот — не украшение, а доказательство честности. Пользователь видит физический процесс, прежде чем получить текст.

### Состояния
- **Загрузка:** тасовка (анимация без «подмены» результата), не спиннер.
- **Пусто (история пуста):** не «здесь пока пусто», а «Первый расклад? Начни с одной карты» → `spread=one`.
- **Ошибка draw:** ChatDenied → paywall с ценой; сетевой сбой → повтор, вопрос сохранён.
- **Ошибка interpret:** трактовка не удаляет карты; повтор возможен, повторный вызов возвращает сохранённый текст.
- **Доступность:** `prefers-reduced-motion` → мгновенное открытие без переворота. Клавиатурная навигация по картам. Порядок открытия соблюдается, но не блокирует: карту можно открыть в любой момент подсказкой, а не запретом.

## 5. Люди и временная линия (People / Person Profile / Relationship Timeline)

**Цель:** превратить плоский список фактов и таблицу `partners` в историю отношений. Это самая большая новая продуктов работа v2.

### 5.1 Поток

```
[7. PEOPLE]
   список людей: аватар/инициалы, имя, relation, «что нового»
        │
   ├── + добавить человека → bottom sheet: имя, relation, дата рождения (опц.)
   ├── тап по человеку ──▶ [8. PERSON PROFILE]
   └── тап по «линия» ──▶ [9. RELATIONSHIP TIMELINE]
```

### 5.2 Person Profile
Единая карточка человека: данные рождения (для совместимости), связь, и **всё, что с ним связано** — упоминания в памяти, расклады, где он был темой, записи дневника, разговоры.

Структура сверху вниз: шапка (имя, связь, действия) → «Что я знаю» (факты, привязанные к человеку) → «Наши чтения» (расклады с его участием) → «Разговоры» (**только метаданные**: заголовок треда и число сообщений, без текста) → действия: совместимость, спросить Oracle об этом человеке, удалить.

### 5.3 Relationship Timeline
Обратная хронология: события, чувства, чтения, разговоры по линии отношений. Группировка по месяцу. Это не лента соцсети, а управляемая личная история.

### 5.4 Данные и связи
Текущее состояние: `partners(id, tg_id, name, relation, birth_date, birth_time, birth_city, birth_lat, birth_lon, tz, chart_json)`, а память — плоские строки в `memories` без ссылки на человека. History-эндпоинт `GET /api/history` отдаёт только метаданные (`kind, entry_id, source_id, evidence_id, deep_link, preview ≤160`), и palm намеренно исключён.

Решение (детали — `ARCHITECTURE.md` §Память): аддитивный граф связей, **без удаления и без миграции существующих строк**. Люди остаются в `partners`; добавляется связь «факт ↔ человек», «расклад ↔ человек», «событие ↔ человек».

### Точки отказа
| Ситуация | Поведение |
|---|---|
| Память выключена (`memory_enabled=0`) | Люди и профиль человека видны (read), но «помнить» выключено: явная плашка с кнопкой «Включить память». Блоки «Что я знаю», «Разговоры» и события — пусты; запись (`POST`) отдаёт 409 |
| Нет людей | Не пустой экран: предложение добавить из диалога («Расскажи о нём — я запомню») |
| Удаление человека | Подтверждение с объяснением, что удалится; связанные факты теряют связь, но не удаляются автоматически |
| «Отвязать факт» | `GET /api/memories/{id}` → блок `links` → `DELETE /api/memory-links/{link_id}`. Сам факт сохраняется |
| Чужой `personId` | 404 «не найдено» — единый ответ для чужого и несуществующего (не палим существование) |

## 6. Натальная карта (My Chart)

**Цель:** не таблица планет, а визуализация, которую хочется рассмотреть.

### Поток

```
[12. MY CHART]
        │
   GET /api/chart  ───нет карты───▶ пустое состояние: «Скажи дату рождения»
        │                                  │
        │                            PATCH/POST /api/profile {birth_*}
        ▼                                  ▼
   SVG-колесо: точки, знаки, дома, аспекты
        │
   ├── тап по планете → bottom sheet: что значит в её жизни
   ├── «Разобрать» → POST /api/chart/interpret (llm)
   ├── «Моя Матрица» → GET /api/matrix → арканы
   └── «Совместимость» → выбор партнёра → POST /api/compat/full
```

### Обязательная честность
Если `time_known=false` или `birth_time_precision ∈ {unknown, approx}` — **дома и асцендент не показываются**, и интерфейс явно говорит почему. Старый код уже так делает (`interpretation.validate_chart_text` отклоняет ссылки на дома при неизвестном времени). Новый интерфейс не должен это разрушать.

### Состояния
- **Загрузка:** скелетон колеса, не спиннер.
- **Пусто:** запрос даты прямо на экране, без перехода в настройки.
- **Ошибка `birth_time_precision`:** кнопка «Уточнить время» → `/settings`.
- **Успех:** колесо + 3 акцента («самое заметное в карте»), не 20 планет без приоритета.

## 7. Память и паттерны (My Patterns / Memory)

**Цель:** продуктовая отстройка. Пользователь должен видеть, что Oracle помнит, и управлять этим.

### Поток

```
[13. MY PATTERNS / MEMORY]
        │
   GET /api/memories  ───память off───▶ экран-объяснение + «Включить память»
        │
        ▼
   ┌─ «Что ты обо мне знаешь» — факты, сгруппированы по kind ─┐
   │  каждыи: редактировать / удалить / отвязать от человека    │
   └───────────────────────────────────────────────────────────┘   │
   ├── «Что я вижу в паттернах» — синтез (НЕ новые факты,  │
   │   а пересказ сохранённого; помечено как наблюдение)  │
   ├── «События и люди» — граф связей                    │
   └── «Экспорт» / «Удалить всё»                        │
```

### Жёсткие правила
1. **Отключённая память не используется.** Consent проверяется в трёх местах, включая сами инструменты: `tool_registry.py:937,950,960` — «Tool calls are model-generated and must never be able to user's setting». Промпт-инъекция не может включить память.
2. **Сохранённое не смешивается с предположением.** В UI элементы делятся на «факт (сохранила с твоих слов)» и «наблюдение (это моя трактовка)». Разные визуальные маркировки, не одна карточка.
3. **Удаление точечное.** `DELETE /api/memories/{id}`; аккаунт — `POST /api/account/delete` с анонимизацией и очисткой всех связанных таблиц.
4. **Изоляция.** Параметра `tg_id` в контракте нет; owner-scope на уровне SQL.

### Состояния
- **Пусто:** не «память пуста», а «Расскажи что-нибудь — и я запомню» + 3 примера.
- **Память off:** объяснение, что именно не работает (персонализация), кнопка включения, не затемнение интерфейса.
- **Ошибка удаления:** оптимистичное удаление с откатом и повтором.

## 8. Оплата (Paywall)

**Цель:** не блокировать, а объяснять. Paywall появляется в момент истины, когда пользователь уже получил ценность.

### Поток

```
[14. PAYWALL]  ◀── лимит вопросов / премиум-расклад / отчёт
        │
   GET /api/entitlements, GET /api/shop
        │
   ├── «На сегодня вопросы кончились»
   │     ├── купить кристаллы (POST /api/shop/crystals → Stars)
   │     └── оформить подписку (POST /api/shop/web-checkout → Paddle)
   └── «Этот расклад премиум»
             └── Stars invoice / кристаллы
```

### Правила
- Никогда не показывать до первого полезного ответа.
- Показывать, **что именно** кончилось: вопросы сегодня / конкретный расклад / отчёт.
- Уважать отказ: кнопка «Не сейчас» не исчезает и не уменьшается.
- Bot Mini App никогда не выдаёт товар напрямую: он создаёт заказ и ссылку, fulfilment приходит боту (`app/api/routers/shop.py:1-6`).

[15. ME / SETTINGS]
   GET /api/me
   │
   ├── Профиль: имя, город, дата/время рождения, точность
   │     PATCH /api/profile

   ├── Уведомления: GET/PATCH /api/notifications/preferences
   ├── Подписка и платежи: GET /api/shop/orders, /payment-history
   └── Удалить аккаунт: POST /api/account/delete {confirm:true}
```

### Возрастная политика
Продукт 16+. В старом коде проверка возраста **удалена** миграцией `0006_drop_age_columns` (колонки `age_confirmed`/`age_proof_hash` убраны, `confirmed_age_user` стал алиасом `current_user`).

В v2 возвращается **самоподтверждение** через поле `age_confirmed` в `PATCH /api/profile`: шаг 16+ в онбординге обязателен, сервер пишет `age_confirmed_at = now()`.

Граница гейта:
- Гейт наложен **только на `active_user`** (платный контент: `/api/today`, `/api/compat/full`, `/api/synastry`, `/api/composite`, `/api/transits`, `/api/returns`, `/api/chart/pdf`).
- Read-ручки (`/api/me`, `/api/chat/oracle`, `/api/chart`, `/api/memories`) **не гейтируются** — обратная совместимость для пользователей, зарегистрированных до введения гейта.

**Самоподтверждение 16+ не является верификацией возраста.** Юридический вопрос (достаточно ли «мне 16+» для целевых юрисдикций) открыт — `ARCHITECTURE.md` §5.1. Данный гейт снижает риск, но не закрывает его.

## 10. Матрица состояний (обязательна для каждого экрана)

| Состояние | Требование |
|---|---|
| Loading | Скелетон соответствующей формы (карты → колода, карта → колесо), не глобальный спиннер |
| Empty | Один живой призыв к действию, не «Данных нет» |
| Error | Человеческий текст + «Попробовать снова»; без кодов и стектрейсов; черновик сохранён |
| Success | Понятный результат + при необходимости доказательная подпись |
| Retry | Идемпотентность через `X-Idempotency-Key`; повтор мутации безопасен |
| Offline | Объяснение + сохранение ввода + автоповтор при появлении сети |
| Reduced motion | Все анимации отключаются; контент доступен мгновенно |
| A11y | Роли, aria-live для ответов Oracle, focus-trap в модалках, target ≥44×44 |
