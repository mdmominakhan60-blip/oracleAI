## 2. Карта переходов (navigation map)

### 2.1. Mobile (<768): нижняя навигация 64px + safe area
- **Чат** — дом по умолчанию после онбординга; внутри открытого разговора нижняя навигация скрывается, свайп-назад/кнопка «Назад» возвращают к списку диалогов (§3.1).
- **Сегодня** — заголовок, контент, без нижних вложенных табов.
- **Библиотека** — 3 таба сегмент-контролом (Разборы · Диалоги · Дневник), таб = состояние раздела, не отдельный экран.
- **Профиль** — список секций (данные рождения, партнёры, память, уведомления, язык/оформление, тариф, помощь, данные). Подраздел профиля — push-переход с заголовком-«Назад», не модалка.

### 2.2. Tablet (768–1279): левый рельс 72px + drawer истории
- Рельс: иконка+подпись 4 разделов; история диалогов — drawer слева; активный инструмент — поверх рабочей области или отдельным экраном (если параллельные колонки < минимальной ширины формы/переписки). Определять по ширине окна, не по UA (§3.2).

### 2.3. Desktop (≥1280): sidebar 224px + центральная колонка ≤760px + правая панель 360px
- Sidebar: бренд, «Новый разговор», 4 раздела, недавние диалоги, профиль внизу.
- Таро/карта/сравнение — расширенная сцена в центральной области; разговор сворачивается в доступную боковую вкладку и возвращается без потери позиции (§3.3). Максимум 3 колонки на 1280; четвёртой колонки агентов нет.
- Контейнер ≤1680px, внешние поля ≥24px, межколоночный отступ 24px.

### 2.4. Дерево путей (канонические route-коды для нового роутера)
```
/                        → редирект по состоянию (S01/S03/Чат)
/onboarding              → S04 (шаги, свои Back-правила)
/chat                    → S07 список диалогов
/chat/:conversation_id   → S06 разговор (нав скрыта на mobile)
/chat/new                → S05 (agent=?); «Новый» никогда не удаляет текущий (§3.4)
/chat/new/agent/:code    → S08/S09 выбор агента → создать диалог
/tools                   → S10 sheet (не standalone-роут; открывается из чата)
/tools/:tool_id          → S11 workspace (fullscreen mobile / сцена desktop)
/results/:result_id      → S12 детальный вид (из чата или библиотеки)
/today                   → S15
/library(/readings|/sessions|/diary) → S20
/profile                 → S21 (+ подразделы /birth, /partners, /memory,
                            /notifications, /language, /plan, /help, /data)
/paywall?return_to=…     → S24 sheet: return_to — единственный путь назад к черновику
```
Правило: route существует только у самостоятельных состояний (§11 «экран ≠ URL»); sheet/space-оверлеи в историю не пишутся как отдельные записи — Back закрывает верхнее временное состояние, затем идёт по стеку (§3.4).

**Запрет (§3.4):** не должно быть случая, когда browser Back уходит с сайта, а Telegram Back закрывает только окно. Реализация: единый стек истории; BackButton-хендлер = тот же pop перехода.

**Переключение агента:** не переименовывает разговор, не переносит контекст; «обсудить с другим» — новый диалог с передачей только выбранного результата и минимального контекста (§3.4). Черновики изолированы по разговору×инструменту, при переключении не отправляются.

## 4. Сценарии сквозных путей (input для QA E-сцен)

### 4.1. Новый пользователь (E01)
`S01 → S03 → S04 (язык→имя→пол→рождение [ BirthDate/Time/CityFields, R10 ]) → Чат (S05 пустое состояние Лилит) → «Инструменты» → Таро без принудительного рождения → результат → обсуждение`
- Таро не требует данных рождения (E01: «не вынужден вводить ненужное»); карта/синастрия — запрашивают свои данные в момент первого использования через workspace.

### 4.2. Возвращающийся
`S01 restore → Чат: последний активный диалог на desktop / список на mobile (решение: mobile по умолчанию список, т.к. одна рука+одна цель; desktop — последний диалог) → продолжение` — draft и позиция скролла каждого диалога сохранены (§4).

### 4.3. Инструмент → результат → библиотека (§5.3 жизненный цикл)
`Чат → каталог → выбор (не платный) → требования → ввод → проверка (валидация/доступ/стоимость ДО запроса) → выполнение (статус в разговоре) → результат в чате (превью) → S12 детально → «В библиотеку» | «Обсудить»`
- Ветви: ошибка ввода → исправление на месте; нет доступа → paywall (H6) → возврат к тому же черновику; сбой → проверить статус/повторить (не двойное списание E17); закрытие workspace ≠ отмена операции.

### 4.4. Оплата (E16/E17)
`ограничение → paywall sheet (цена от сервера) → купить → внешний провайдер → возврат → server-state sync (pending≠failed) → return_to: тот же инструмент/вопрос/форма` + тариф доступен всегда из Профиля.

## 5. Ключевые правила проектирования (binding для R03+)

1. **Чат — дом.** После онбординга старт в Чате; всё остальное достижимо ≤2 переходов от нижней навигации.
2. **Навигация — состояние, не модалка.** Открытый диалог на mobile скрывает нижнюю навигацию (§3.1); на desktop sidebar постоянен.
3. **Временное ≠ постоянное.** Sheet/workspace пишутся в один back-стек; подтверждение удаления — только у деструктивных действий; обычное меню без подтверждения (§3.4).
4. **Клавиатура:** уменьшает переписку, composer доступен, декоративные высоты не сохраняются (§3.1). Проверка на реальных Telegram WebViews (§16.2 прим.).
5. **320px без горизонтального скролла; отступ 16px; проверка resize у 768/1280 (§16.2 матрица).**
6. **Desktop ≠ растянутый телефон:** sidebar 224px + центральная ≤760px (60–75 симв./строку) + панель 360px; 3 колонки максимум.
7. **Каждый переход определён в реестре действий** (§11): action ID, RU/EN label, accessible name, условие видимости, вход, переход/эффект, стоимость, pending/error/success, Back/close, права, аналитика, тест. Не оставлять «по нажатию что-нибудь откроется».
8. **Контекст разговора привязан к conversation_id + operation ID**, не к DOM (§5.3): смена экрана/агента не переносит результат в другой диалог (фикс известного дефекта `go()` — сейчас `chat.key=null` при смене вью).
