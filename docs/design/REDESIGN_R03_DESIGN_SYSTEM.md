# R03 — Дизайн-система OracleAI
**Задача:** BUS-731 (волна A эпика BUS-721 «новый дизайн»). **Вход:** план BUS-721 §2, §5.2, §7.3, §11.2, §13.1, §14.2; R02 IA (`REDESIGN_R02_IA_NAVIGATION.md`, коммит `7f7cd3b`); R01 baseline (`REDESIGN_R01_BASELINE_INVENTORY.md`, `8fbb477`).
**Статус:** проект к независимой приёмке Engineering Lead.
**Сверено с кодом:** токены `miniapp/css/00-tokens.css` (семантические + ~40 legacy-алиасов), шрифты `miniapp/fonts/oracle-fonts.css` (Cinzel 500/600/700 + Plus Jakarta Sans, self-hosted WOFF2), CSS-модули `miniapp/css/00–21` (21 файл, dirty-правки BUS-741).

## 0. Роль этого документа

Этот документ — **нормативная фиксация системы** (single source of truth), на которую ссылаются все последующие макеты R-волны и дизайн-ревью реализованных фич. Он фиксирует: характер (§1), токены (§2), типографику и кириллицу (§3), компоненты (§4), шаблоны инструментов (§5), motion (§6), ограничение визуальной нагрузки (§7), состояния и доступность (§8), правила расширения и design review (§9), владельца системы (§10).

Принцип плана §2.2: **размеры важнее абсолютной идентичности пикселя** — увеличенный текст должен переноситься, а не обрезаться. Токены здесь — конкретные стартовые значения плана, прошедшие проверку контраста (§2.4); дальнейшие изменения централизуются в этом документе через доп. ревизию, не в локальных CSS модулях.

## 1. Характер визуала (план §2.1)

Ночное персональное пространство: глубокий индиго, тёплый свет шампанского, тонкие орбитальные линии, спокойные поверхности, крупный читаемый текст. Выразительность — портреты, карты, живой фон; рабочие элементы компактны и предсказуемы.

Отличия от Селены (антиреференс): дисциплину последовательности — берём; оранжевые кнопки, фон, фотографии, тексты, стеклянные рамки во множестве слоёв — не копируем.

Проверка характера при ревью: любой экран можно описать предложением «ночь, один тёплый акцент, контент спокоен». Если на экране два конкурирующих акцента или «праздничный» рабочий элемент — это отступление от системы.

## 2. Дизайн-токены

### 2.1. Цвета

Семантические имена (не «gold», а «accent»): компоненты ссылаются только на семантический слой.

| Токен | Значение | Назначение |
| --- | --- | --- |
| `--color-bg` | `#0B0D18` | Общая ночь (фон приложения) |
| `--color-surface` | `#141827` | Подложка чтения и формы |
| `--color-surface-raised` | `#1C2233` | Меню и вторичные контейнеры |
| `--color-surface-overlay` | `#242C3F` | Модальные поверхности, sheet |
| `--color-text-primary` | `#F4F2ED` | Основной текст |
| `--color-text-secondary` | `#B7BDCB` | Пояснения |
| `--color-text-muted` | `#9AA4B8` | Метаданные, остающиеся читаемыми |
| `--color-accent` | `#E9C982` | Главное действие и фокус |
| `--color-accent-hover` | `#F1D99F` | Наведение главной кнопки |
| `--color-on-accent` | `#1C1820` | Текст на светлой кнопке |
| `--color-border` | `#384256` | Декоративные разделители (не интерактивные) |
| `--color-border-control` | `#717B96` | Границы интерактивных контролов (уточнение, см. §2.4) |
| `--color-success` | `#97D8BD` | Успех (всегда с текстом и значком) |
| `--color-error` | `#F1A4AA` | Ошибка (всегда с текстом и значком) |
| `--color-info` | `#ABC9EF` | Инфо (всегда с текстом и значком) |

Производные слои (допускаются как производные от семантических, не как новые цвета):

- `--focus-ring`: `0 0 0 3px rgba(233, 201, 130, .35)` — видим на всех четырёх поверхностях.
- `--hover-bg`: `rgba(233, 201, 130, .08)`; `--hover-border`: `rgba(233, 201, 130, .35)` — единые hover/focus-слои, компоненты не изобретают свои rgba.
- Тень одна: `--shadow-overlay: 0 18px 50px -18px rgba(0,0,0,.85)` — только для меню, popover, sheet/модалок. Постоянно светящиеся контуры обычных карточек запрещены (план §2.2).
- Градиент акцента — единый `--grad-primary` (вертикаль `#F1D99F → #E9C982`), определён один раз; ручное размножение градиента в селекторах запрещено (урок BUS-712: 7 селекторов с ручными копиями).

Запрещено: новые hex-значения в CSS-модулях, минуя этот файл; «временно» новые постоянные цветовые полосы; пятая непрерывная анимация цвета.

### 2.2. Радиусы, отступы, размеры

- Отступы: шкала 4/8/12/16/24/32/48 (`--space-1…6`). Между смысловыми секциями — 24, внутри формы — 16.
- Радиусы: контрол 12 (`--radius-control`), карточка 16 (`--radius-card`), большой sheet 24 (`--radius-sheet`); 999 — только chip и аватар. Весь экран из капсул не делать.
- Кнопки: главная 48 px по высоте, вторичная 44–48; иконка 20–24 px внутри области нажатия ≥44×44 CSS px (внутренний стандарт; WCAG 2.2 AA Target Size 24×24 — юридический минимум, мы строже).
- Композитная сетка: gutter 16 (mobile) / 24 (desktop), контейнер ≤1680, боковые поля ≥24 (desktop, из R02 §2.3).

### 2.3. Тёмная/светлая тема

Продукт — «ночная» идентичность (§1): светлая тема **не входит в скоуп волны A**. Токены закрепляются за `:root` без медиа-запроса `prefers-color-scheme` (полуночная палитра — часть бренда, а не выбор инверсии). Если волна B решит добавить светлую тему — это доп. ревизия этого документа с полным прогоном контраста по §2.4, не локальная замена hex.

### 2.4. Проверка контраста (выполнена 2026-09-10, WCAG 2.2 AA)

Метод: относительная яркость sRGB, пары «текст × поверхность», минимальная композиция (прозрачные слои поверх фона дают ту же пару). Результаты:

- Все текстовые пары плана проходят AA с запасом: text-primary 12.4–17.3; text-secondary 8.4–10.3; text-muted 6.3–7.7 (все ≥4.5:1 на всех четырёх поверхностях).
- `on-accent #1C1820` на `accent #E9C982` — 10.9; на `accent-hover #F1D99F` — 12.6.
- Статусы (success/error/info) на surface — 8.9–10.8, на bg — 9.8–11.9.
- **Уточнение к плану (право дизайн-лида §2.2):** `border #384256` как цвет интерактивных контролов не проходит 3:1 (1.57–2.81 на поверхностях). Введён `--color-border-control: #717B96` (3.0–4.6 на всех четырёх поверхностях — от bg до overlay). `#384256` остаётся для декоративных разделителей, где 3:1 не применим (non-essential).
- `accent` как текст-ссылка на bg/surface — 11.0–12.1; на accent-кнопке различимость hover — через тень/градиент, а не только цвет (дельта 1.15 недостаточна как единственный признак).

Ограничение: это проверка пар токенов, не финальных композиций с изображениями — при дизайн-ревью фич (§9) контраст меряется на реальных экранах.

### 3.1. Шрифт

- Основной и заголовочный: **Manrope** (план §2.2), self-hosted WOFF2, начертания 400/500/600/700, с реальной кириллицей. Лицензия OFL; проверить набор глифов и размер файлов перед поставкой (метаданные — Google Fonts ofl/manrope).

## 5. Шаблоны инструментов (план §5.2, реестр)

Каждая новая функция регистрируется в реестре инструментов (§9.1) и выбирает **один из трёх шаблонов запуска** — отдельный стиль/мастер «на одну функцию» не заводится:

| Шаблон | Примеры | Пространство | В разговоре остаётся |
| --- | --- | --- | --- |
| Быстрый | Прогноз, готовая Луна | проверка доступа/данных → запуск, без искусственного мастера | короткий результат + открыть/обсудить |
| Форма | Дата/город, партнёр, дневник, отчёт | полный экран mobile; правая панель desktop, если помещается | резюме действия, не вся форма |
| Интерактивная сцена | Таро, натальная карта, ладонь, сложная совместимость | полный экран mobile; большая центральная сцена desktop | превью результата с постоянной ссылкой |

Правила: выбор инструмента сам по себе не запускает платную операцию; на последнем шаге явно показываются стоимость/доступ и действие («Построить»/«Получить разбор»/«Отправить фото»); известные данные профиля подставляются с возможностью проверки; после ошибки оплата не повторяется без сверки статуса (E17).

## 6. Motion (план §7.3)

### 6.1. Спецификация событий

| Событие | Длительность/характер | Спокойный режим |
| --- | --- | --- |
| Кнопка/выбор | 120–160 мс, цвет/opacity | мгновенное состояние |
| Sheet/панель | 180–240 мс, translate+opacity | короткое появление без перемещения |
| Переход шага | 180–220 мс, с сохранением оси | без слайда |
| Переворот Таро | 450–600 мс на карту, ограниченная очередь | сразу показывать выбранные карты |
| Портрет при выборе агента | мягкое появление 200–300 мс, однократно | статический портрет |
| Туманность | цикл 30–60 с, движение до 1–2% | статичная композиция |
| Звёзды | редкое мерцание; максимум один заметный метеор | без движения |

Токены: `--motion-quick: 140ms`, `--motion-base: 220ms`, `--motion-slow: 480ms`, `--ease: cubic-bezier(.22, 1, .36, 1)` — единый темп, компоненты не задают свои длительности.

### 6.2. Ограничения

- Движение преимущественно transform/opacity; большие blur, layout-размеры, background-position не анимировать без измерения стоимости; will-change не держать на каждом элементе.
- Никакого звука по умолчанию; говорящие лица/фоновые видео не входят в первую версию.
- Постоянно движущийся фон требует пользовательской настройки «Анимация фона» (пауза) — **reduced motion не заменяет кнопку паузы** (W3C Pause-Stop-Hide).
- Остановка на скрытой вкладке (`visibilitychange`).

### 6.3. Reduced motion

`prefers-reduced-motion: reduce` — на уровне системы (единый блок в токенах, не в каждом модуле): карты появляются без 3D-поворота, sheet/шаги — без перемещения, туманность/звёзды — статичные композиции, портрет — статический. Проверка каждого нового паттерна — на mobile+desktop в обоих режимах.

## 7. Ограничение визуальной нагрузки (план §2.3, проверка ревью)

1. Одна доминирующая кнопка на экран в обычном состоянии.
2. Системная навигация выделяет выбранный раздел спокойной подложкой/индикатором — без яркого золотого прямоугольника размером с CTA.
3. Карточка: один заголовок, одна краткая поясняющая строка, одно основное действие.
4. Вложенность поверхностей — максимум два смысловых уровня (surface → surface-raised; overlay только модальные).
5. Ограничения служат порядку, не сокрытию: длинный результат доступен полностью, каталог имеет поиск/категории, функция не исчезает ради скриншота.

## 8. Состояния и доступность

### 8.1. Обязательная матрица состояний (план §11.2)

Для каждого S-экрана рисуются до разработки: initial/loading; пусто; данные; длинные данные; некорректный ввод; submitting; частичный/ожидающий результат; success; network error/offline; session expired; нет доступа; недоступная функция; удалённый/несуществующий объект. Для элементов: default, hover (где доступен), focus-visible, pressed, selected, disabled, loading. Неприменимость — явно в матрице, не пустой клеткой.

### 8.2. Доступность (план §13.1, WCAG 2.2 AA)

- Контраст: §2.4; меряется на финальной композиции (изображения/прозрачность), не только пары токенов.
- Touch target ≥44×44 (внутренний стандарт); иконка может быть меньше внутри большой области.
- Клавиатура: весь основной путь; focus-visible всегда виден (`--focus-ring`); логичный Tab; никаких hover-only меню и обязательного drag.
- Modal/sheet — по Dialog Pattern; CityCombobox — по Combobox Pattern; карты имеют название позиции и текстовую альтернативу схемы расклада; календарь — доступная навигация по датам.
- Ошибки не только цветом; статус сообщается без перечитывания всего длинного ответа на каждый токен; aria-live не перебивает чтение при стриминге.
- **200% текста и 320px:** фиксированные высоты под текст не заводятся (min-height, а не height); при увеличении до 200% текст переносится, страница не уезжает горизонтально; визуализация может иметь собственное осмысленное увеличение.
- Фиксированный footer (composer) не скрывает фокус/ошибку.

### 8.3. Состояния элементов (свод)

default / hover / focus-visible / pressed / selected / disabled / loading — для каждого компонента §4; неприменимые отмечаются явно.

## 9. Правила расширения (план §14.2, normative)

### 9.1. Реестр функций (registry)

Любая следующая функция обязана зарегистрировать: ID/агента; цель; категорию каталога; требования данных/доступа; **один из трёх шаблонов (§5)**; результат/историю; действия/ошибки; зависимости; тесты. Форма записи — строка реестра инструментов (продолжение §10–§11 плана; ведётся в этом же каталоге `docs/design/`).

### 9.2. Запреты (не повторить беспорядок)

Запрещено добавлять «временно»: новую постоянную полосу в чат; ещё один тарифный блок в шапку; пятую глобальную вкладку без пересмотра IA; отдельный стиль карточки на одну функцию; новую цепочку `!important`; глобальный monkey-patch обработчика. Новый UI-паттерн сначала появляется в библиотеке компонентов (§4) и проверяется на mobile+desktop, затем используется в функции.

### 9.3. Правило design review

1. Каждая фича перед приёмкой проходит дизайн-ревью владельца системы (§10) или назначенного ревьюера: соответствие токенам (нет новых hex/размеров вне шкал), компонентам (реиспользование или зарегистрированный новый вариант), §7 (нагрузка), §8 (состояния/a11y).
2. Ревью на реальных размерах (mobile 320–430, desktop ≥1280), а не только на увеличенном артборде; grep-критерии унификации (из BUS-712 §3) запускаются на diff.
3. Вердикт: соответствие / расхождения с перечнем и ссылкой на пункт этого документа. Расхождение — либо фикс, либо доп. ревизия системы (не локальный обход).
4. Готовность функции (план §14.2): доступна из понятного места; есть все состояния; сохраняются контекст/данные; действие реально работает; добавлены тесты и визуальные эталоны. Красивое изображение без рабочего сценария не означает готовность.

### 9.4. Процесс изменения системы

Изменение токенов/компонентов = доп. ревизия этого документа (короткий diff-блок «Ревизия N: что и почему, проверка контраста/состояний») + коммит в эту же папку. Локальные правки CSS-модулей, расходящиеся с документом, — дефект ревью, а не «эволюция».
