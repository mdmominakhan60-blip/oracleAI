# Политика LLM-контекста OracleAI

**Статус:** production contract, v76  
**Обновлено:** 12 августа 2026  
**Область:** `app/core/agents/`, `app/core/memory.py`, `app/repo/dialog.py`

## 1. Цель и границы

Этот документ фиксирует, какие данные попадают в запрос к языковой модели OracleAI, как ограничивается история, когда сбрасывается краткосрочный контекст и как пользовательский режим памяти влияет на следующий ответ. Он предназначен для разработчиков, QA и авторов новых инструментов; изменения этих правил требуют обновления этого документа и регрессионных тестов.

> **Главное различие:** история чата — краткосрочный контекст одного треда. Память — отдельный, пользовательски управляемый набор фактов. Новый тред очищает историю, но не удаляет память. Пауза памяти исключает факты из prompt, но не уничтожает их и не скрывает от владельца.

## 2. Состав LLM-запроса

Вызов агента формируется в `app/core/agents/runtime.py::answer`. Запрос состоит из одного системного сообщения, ограниченной истории текущего треда и текущего вопроса, который присутствует **ровно один раз**. Инструменты передаются отдельно в tool-use цикл.

| Блок | Источник | Когда передаётся | Назначение |
| --- | --- | --- | --- |
| Идентичность проводника | `AgentSpec`, контент-override и persona | Всегда | Роль, тон, доступные навыки и правила проводника |
| Профиль | Пользователь, натальная карта, матрица | Всегда, если данные существуют | Даёт персональный, но ограниченный фактами контекст |
| Выборочная память | `memory.recall()` | Только при `memory_enabled=true` | Семантически релевантные факты в лимите тарифа |
| Сводка профиля | `memory.get_summary()` | При доступной глубине памяти более 5 | Короткая долговременная сводка вместо полного массива фактов |
| Правила диалога | `DIALOG_BASE`, `SYNTHESIS_PROTOCOL`, правила агента | Всегда | Бережная речь, evidence-first и практический следующий шаг |
| Лимиты и safety | allowance line, `SAFETY`, кризисные и языковые правила | Всегда; extra rules идут последними | Запрет выдумывать расчёты, опасные прогнозы и финансово-медицинские гарантии |
| История треда | `dialog_repo.history()` → `build_bounded_history()` | Только для переданного `thread_id` | Непрерывность одного диалога при предсказуемом размере prompt |
| Tools | `skills.tools_for(spec.skills)` | Только разрешённые проводнику | Получение реальных расчётов и операций; результаты возвращаются в agent loop |

Системный prompt собирается в `app/core/agents/base.py::build_system_prompt`. Его порядок намеренный: идентичность и контекст → правила качества → правила конкретного проводника → лимиты → safety, затем экстренные/языковые дополнительные правила. Последние блоки имеют приоритет над образом агента.

## 3. Правила памяти

`runtime._context()` рассчитывает глубину retrieval по тарифу. Если память выключена, функция возвращает пустые память и сводку: модель не получает сохранённые факты. Если память включена, `memory.recall()` выбирает данные по релевантности к текущему вопросу, а не просто первые записи; это защищает от нерелевантного переноса тем между вопросами.

| Событие | Поведение |
| --- | --- |
| Пользовательница выключает память | Следующий prompt не содержит фактов или summary; архив остаётся доступен только владельцу |
| Пользовательница включает память | Новый ответ снова может использовать релевантные факты в пределах тарифа |
| Добавляется или изменяется факт | Кэш retrieval инвалидируется; следующий запрос видит актуальное состояние |
| Удаляется факт или очищается архив | Кэш инвалидируется; факт не должен попасть в следующий prompt |
| Дневниковая запись | Сохраняется в дневниковом контуре и не считается автоматически фактом долговременной памяти |

Ни UI, ни новый инструмент не должны напрямую добавлять произвольный текст в system prompt. Для добавления факта используется единый контур памяти с дедупликацией и инвалидацией кэша.

## 4. Политика истории и явный сброс

`build_bounded_history()` в `app/core/agents/context.py` принимает историю только одного `thread_id` и вопрос текущего вызова. Она очищает пустые и неподдерживаемые роли, ограничивает длину отдельных сообщений и добавляет текущий вопрос, только если его ещё нет последней пользовательской репликой.

| Условие | Результат |
| --- | --- |
| Новый тред | В БД нет его старой истории; краткосрочный контекст начинается заново |
| История в пределах `recent_limit` | В prompt передаются очищенные реплики в исходном порядке |
| История длиннее лимита | Последние реплики остаются полностью; до четырёх ранних пользовательских тем сжимаются в детерминированный служебный блок |
| Текущий вопрос уже записан в БД | Повторно не добавляется в messages |
| Другой тред | Не запрашивается и не может попасть в список messages |
| Премиум-подписка | Получает увеличенное окно recent history и больше итераций tool-use; принцип изоляции не меняется |

Ранняя выжимка маркируется как темы пользовательницы, а не как новые инструкции. В неё не включаются ранние ответы агента: они не должны превращаться в «факты» или повышать риск prompt-injection через старый текст.

## 5. Инструменты и evidence-first

Модель получает только зарегистрированные у выбранного проводника tools. Когда инструмент вызывается, `skills.execute()` возвращает структурированный результат в agent loop. Системные правила требуют называть доступные наблюдения и отделять их от интерпретации. Карты, планеты и вычисления нельзя выдумывать: источником могут быть только результаты инструментов и надёжные профильные расчёты.

Новый инструмент обязан:

1. быть добавлен в разрешённый набор `AgentSpec` конкретного проводника;
2. возвращать краткий, валидируемый результат, пригодный для показа пользователю;
3. не записывать данные в память без явного пользовательского действия или действующего продуктового контракта;
4. иметь тест на авторизацию, входные данные и отсутствие смешения тредов;
5. не обходить policy через прямую сборку messages.

## 6. Устойчивость ответа

`runtime.answer()` не выбрасывает исключение наружу. При сбое LLM-провайдеров, ошибке tool-use цикла или слишком коротком ответе используется `offline_answer()`. Этот режим строится на реальных локальных расчётах карты и таро, а не возвращает техническую заглушку. Он также уважает `memory_enabled`: при выключенной памяти факты не передаются и в офлайн-ответ.

| Проверка | Файл |
| --- | --- |

При изменении лимитов, ролей, memory toggle, system prompt или поведения summary необходимо обновить тесты и эту политику. Для локальной проверки используются `pytest -q`, `python3 -m py_compile` для затронутых Python-модулей, `node --check` для затронутых JavaScript-модулей и browser QA критических mobile-сценариев.

## 8. Неявные допущения, которые запрещено менять без решения продукта

- Пауза памяти — это не удаление истории и не скрытие архива от пользовательницы.
- Новый тред — единственный UI-механизм явного сброса краткосрочного диалога.
- Краткая выжимка не является LLM-summary: она детерминированна и не требует дополнительного LLM-вызова.
- На один turn текущий вопрос должен быть представлен модели ровно один раз.
- Safety-инструкции и кризисные правила не могут быть заменены persona-текстом, памятью или результатом инструмента.
