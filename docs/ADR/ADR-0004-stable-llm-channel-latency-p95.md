# ADR-0004 — Стабильный LLM-канал / латентность p95 (post-MVP)

**Status:** proposed (final decision deferred to beta data, BUS-110)
**Date:** 2026-09-06
**Task:** BUS-228 (follow-up из CEO verdict по P0-003, BUS-227)
**Owner:** CTO

## Context

Гейт P0-003 закрыт по quality-критериям (zero critical violations, mean 0.84,
language 1.0, calibration 1.0 на `antigravity/gemini-2.5-flash`). Таргет
латентности p95 ≤ 15s снят с MVP-гейтов вердиктом CEO и вынесен в BUS-228.

Канал сейчас — бесплатный omniroute-прокси (host-network, `localhost:20128/v1`,
`.env`: `LLM_PROVIDER=custom`). Верифицированная латентность по обоим прогонам
live-eval (28 запросов, n=28):

| Метрика | Run 1 (n=14) | Run 2 (n=14) | Combined (n=28) |
|---------|--------------|--------------|-----------------|
| median  | 13.6s        | 10.6s        | 12.0s           |
| p90     | 24.9s        | 145.4s       | 133.3s          |
| max     | 63.0s        | 148.5s       | 148.5s          |
| доля < 15s | 10/14     | 10/14        | 18/28 (64%)     |

Распределение **бимодальное**: основная масса запросов 2.6–15.7s, отдельный
кластер выбросов 62s (run 1) и 133–148s (run 2) на идентичных промптах.
Это нестабильность upstream бесплатного прокси-канала, не промптов/кода.
Воспроизводимый p95 ≤ 15s на таком канале недостижим.

**Митигирующие свойства продукта уже есть** (проверено по коду):
- `app/core/llm.py:60` — `TIMEOUT = 35.0` на вызов, `RETRIES = 2` на
  провайдера, затем фейловер по `provider_chain` (`app/config.py:148`).
  Хвост 148s пользователю не пробрасывается: вызов обрывается на 35s,
  ретраи суммарно ≤ ~105s worst-case, дальше — fallback-провайдер или
  офлайн-режим (`core/agents/runtime.py`).
- `llm_usage` (`alembic/schema/baseline.sql`, таблица `llm_usage`) пишет
  `provider, model, latency_ms, ok, purpose` на каждый вызов
  (`app/repo/analytics.py:361`). Бета-период соберёт реальную латентность
  без дополнительной инструментации.

**Вывод:** задача не о том, чтобы «сделать канал стабильным» кодом — код уже
ограничивает ущерб. Задача — выбрать канал, на котором p95 укладывается в
продуктовый таргет, либо пересмотреть таргет.

## Options

### Вариант 1 — платный LLM-провайдер с контрактным SLA
- **Плюсы:** самый быстрый путь к воспроизводимому p95; SLA — договорная
  гарантия, а не наблюдение; минимальная инфра-работа (сменить
  `CUSTOM_LLM_BASE_URL/KEY/MODEL`, цепочка провайдеров уже поддерживает).
- **Минусы:** бюджетное решение владельца/board — вне моих полномочий;
  юнит-экономика «≤ $2.5/мес на платящую клиентку» должна быть перепроверена
  с платными тарифами провайдера.
- **Кандидаты:** любой OpenAI/Anthropic-совместимый API с тарифом и SLA
  (прямой Anthropic API, OpenAI API, или платный прокси с гарантиями).

### Вариант 2 — локальная модель
- **Плюсы:** нет пер-запросной стоимости, полный контроль, нет upstream-хвостов.
- **Минусы:** отдельная инфра-работа (GPU-хост, vLLM/Ollama, эксплуатация,
  бэкапы) — по масштабу отдельный эпик, не follow-up; качество на наших
  eval-кейсах не подтверждено.

### Вариант 3 — пересмотр таргета p95 по фактическим бета-данным
- **Плюсы:** нулевая стоимость; честная калибровка под реальное поведение.
- **Минусы:** не устраняет хвосты — при кластере 133–148s даже смягчённый
  p95-таргет будет нестабильным; риск деградации UX (пользователь ждёт >2 мин
  только чтобы получить отказ по таймауту 35s).

## Decision

**Финальное решение отложено до бета-данных BUS-110** (CEO verdict, BUS-227).
Критерии выбора после бета-периода:

1. **Данные:** перцентили TTFB/total по `llm_usage.latency_ms` за бета-период
   (p50/p90/p95/p99, per-provider, per-model, доля `ok=0`, доля запросов,
   попавших в retry/fallback). Минимум 2 недели живого трафика.
2. **Если p95 фактический ≤ таргет** (начальный таргет 15s или пересмотренный)
   и доля fallback < 1% — вариант 3, фиксируем таргет, задачу закрываем.
3. **Если хвосты повторяются** (p95 > таргет при медиане в норме) — вариант 1:
   готовлю для CEO/board сравнение платных провайдеров (цена/SLA/латентность
   на нашем eval-наборе `scripts/run_llm_eval_live.py`) как бюджетную заявку.
4. **Вариант 2 (локальная модель)** — только если вариант 1 не проходит по
   бюджету или SLA-гарантии оказываются фиктивными на практике.

**Предварительная техническая позиция CTO:** вариант 1 — основной кандидат
(минимальная инфра-работа, продуктовая цепочка уже готова к смене провайдера
без изменений кода), вариант 3 — приемлемый исход, вариант 2 — крайняя мера.

## Consequences

- До беты ничего не меняем в канале: free-канал достаточно хорош для
  controlled beta (BUS-110 non-goal подтверждён).
- Бета-наблюдаемость BUS-110 должна сохранить полноту `llm_usage` (все вызовы,
  включая fallback-и) — это источник данных для решения. Требования к метрикам
  переданы в BUS-110 (комментарий от 2026-09-06).
- При смене провайдера (вариант 1) — обновить `.env` на staging, прогнать
  eval-набор на новом провайдере до переключения прода (quality + latency),
  зафиксировать в CURRENT_STATUS.md.
