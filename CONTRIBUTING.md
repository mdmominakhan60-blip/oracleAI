# Git-политика — oracleAI: master-first

> Канон git-политики продукта. Текущая редакция — DR «Единая git-политика: работа в master»
> (2026-09-12, BUS-1126; требование владельца из BUS-721). Предыдущая редакция — BUS-484.
> Репозиторий находится на этапе командной разработки через Paperclip-агентов.

## Принцип

**Источник истины продукта — ветка `master`** (origin = GitHub, gitlab = резерв, BUS-475).
Финальная версия продукта — head of master. Прод VPS следует master с контролируемым лагом.

## Режим по умолчанию: работа напрямую в master

- **Дефолт для всех инженерных агентов — коммит напрямую в `master`** (commit-push).
- Feature-ветка — **исключение, а не норма**. Разрешена только:
  1. крупная параллельная фича — больше одного агента над одной областью кода;
  2. прямое требование QA-изоляции изменения.
- Создание feature-ветки требует **явно обосновать её в комментарии к задаче до первого коммита**.
- Зонтичные и «инкрементные» ветки (типа unify-all, bus741-increment-2) **запрещены**: их объём вливается в master обычным merge-циклом.
- Одновременно живых feature-веток — **не больше 3**.

## Основная ветка

- **master** — единственная основная ветка. Все релизные состояния берутся из master.
  Вторых long-lived веток (develop, release/*) нет.
- master синхронен: `local master = origin/master = gitlab/master`.
- **Force-push в master запрещён.** Обновление gitlab/master — только fast-forward.

## Feature-ветки (когда исключение применено)

- Формат имени: `feature/<issue>` или `fix/<issue>` (короткое пояснение через дефис).
- Короткоживущая: живёт только на время задачи-носителя.
- **После мержа в master ветка удаляется немедленно** на всех уровнях: локально, origin, gitlab.
  Перед удалением обязательно `git merge-base --is-ancestor <branch> master` — никакой потери коммитов.
- Ветка без активной задачи — мусор; чистится при ближайшей консолидации.

## CI-signal ветки

- Ветки `bus*-ci-signal` (GitLab MR для CI-сигнала, GitHub Actions в биллинг-блоке) создаются
  под конкретный MR и **удаляются сразу после прохождения сигнала**.

## Worktree

- Worktree разрешён для параллельной работы по задачам.
- Ветка worktree закрывается вместе с закрытием issue: `git worktree remove`, затем ветка.
- Мёртвые worktree-записи чистятся через `git worktree prune`.

## Stash-бэкапы

- Stash-бэкапы (ветки вида `busNNN-stash-backup-*`) — **local-only**: не пушить в remotes.
  Не часть истории продукта; удаляются локально после закрытия задачи.

## GitLab-зеркало

- После каждого мержа в master: `git push gitlab master:master` (fast-forward).
- Feature-ветки пушатся в оба remotes; удаление — тоже в оба.

## Чеклист закрытия задачи (feature-ветка, исключение)

1. Мерж в master (PR на GitHub) — CI зелёный.
2. `git merge-base --is-ancestor <branch> master` — проверка перед удалением.
3. `git branch -d <branch>` локально; `git push origin --delete <branch>`;
   `git push gitlab --delete <branch>`.
4. `git worktree remove <path>` (если был worktree) или `git worktree prune`.
5. `git push gitlab master:master` — догнать зеркало.
6. В комментарии к issue: что удалено, что оставлено и почему.

Для работы в master без ветки чеклист сжимается: коммит → push origin master →
`git push gitlab master:master` → итог-комментарий в задаче.

## История решения

- BUS-482/484 (2026-09-07): первая фиксация — master единственная основная ветка,
  ветка на задачу, удаление после влития.
- DR 2026-09-12 (BUS-1126, из BUS-721): усиление — master-first как дефолт,
  ветка = исключение с обоснованием до коммита, ≤3 живых веток, зонтичные запрещены.
