# Git-политика — oracleAI: две ветки master+dev

> Канон git-политики продукта. Текущая редакция — DR «Единая git-политика: две ветки»
> rev 2 (2026-09-12, BUS-1126 + BUS-1128; требование владельца из BUS-721).
> Предыдущие редакции: rev 1 master-first (BUS-1126), исходная — BUS-484.
> Репозиторий находится на этапе командной разработки через Paperclip-агентов.

## Принцип

Ровно **две постоянные ветки**: `master` и `dev` (origin = GitHub, gitlab = резерв, BUS-475).

- **`master`** — эталонная, финальная ветка. Единственный ответ на вопрос «какая версия финальная». **Прод VPS деплоится только с master.**
- **`dev`** — единая рабочая ветка всех инженерных агентов.

## Режим по умолчанию: работа в dev

- **Дефолт для всех инженерных агентов — коммит в `dev`** (commit-push).
- **Мерж `dev → master` — через PR с QA-гейтом**, не реже раза в день при активной разработке (координация — CTO). GitHub Actions в биллинг-блоке — CI-сигнал через GitLab MR из dev.
- Feature-ветки, ci-signal, зонтичные и «инкрементные» ветки — **запрещены как класс**.
- Исключение — только **approve CEO в комментарии к задаче до первого коммита** (QA-изоляция крупной фичи):
  - формат имени `feature/<issue>` или `fix/<issue>`;
  - короткоживущая, живёт только на время задачи-носителя;
  - **после влива удаляется немедленно** на всех уровнях (локально, origin, gitlab) + worktree задачи.

## Синхронизация

- master синхронен: `local master = origin/master = gitlab/master`.
- **Force-push в master и dev запрещён.** Обновление gitlab-зеркала — только fast-forward.
- После каждого мержа dev→master: `git push gitlab master:master` (догнать зеркало).

## Worktree

- Worktree разрешён для параллельной работы по задачам.
- Worktree закрывается вместе с закрытием issue: `git worktree remove`, затем ветка (если была веткой-исключением).
- Мёртвые worktree-записи чистятся через `git worktree prune`.

## Stash-бэкапы

- Stash-бэкапы (ветки вида `busNNN-stash-backup-*`) — **local-only**: не пушить в remotes.
  Не часть истории продукта; удаляются локально после закрытия задачи.

## Чеклист мержа dev→master (регулярный)

1. PR dev→master на GitHub + QA-гейт (`request_confirmation` на QA/EL по контексту).
2. `gh pr merge` — смержить PR.
3. Финальная верификация master в чистом worktree.
4. `git push gitlab master:master` — догнать зеркало.
5. Итог-комментарий в задаче-носителе мержа.

## Чеклист закрытия задачи с веткой-исключением (только по approve CEO)

1. Влив в `dev` (или PR в master, если исключение требует изоляции от dev).
2. `git merge-base --is-ancestor <branch> dev` — проверка перед удалением.
3. `git branch -d <branch>` локально; `git push origin --delete <branch>`;
   `git push gitlab --delete <branch>`.
4. `git worktree remove <path>` (если был worktree) или `git worktree prune`.
5. В комментарии к issue: что удалено, что оставлено и почему.

Для обычной работы (99% случаев) чеклист сжимается: коммит в dev → push origin dev →
`git push gitlab dev:dev` → итог-комментарий в задаче.

## Переходный период (волна B, BUS-1070)

- Ветки `bus1070-*` не трогать до закрытия BUS-1103/1104/1105.
- После закрытия BUS-1105: `bus1070-wave-b-p3` вливается в `dev`, ветки волны удаляются,
  волна переезжает на dev-модель без своих веток.

## История решения

- BUS-482/484 (2026-09-07): первая фиксация — master единственная основная ветка.
- DR 2026-09-12 rev 1 (BUS-1126, из BUS-721): master-first как дефолт.
- DR 2026-09-12 rev 2 (BUS-1128): модель ровно двух постоянных веток master+dev;
  feature-ветки запрещены как класс, исключение — approve CEO до первого коммита.
