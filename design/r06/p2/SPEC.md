## 2. Что покрыто и по какому требованию

### 2.1 Шаблон «Быстрый» S11a (план §5.2)
- Доступ и данные проверены до запуска: остаток тарифа виден («3 прогноза в день. Использовано 1 из 3»), данные профиля подставлены с пометкой «Изменить данные» на самом шаблоне — подстройка профиля не спрятана в мастер запуска.
- Одно поле (дата прогноза), hint с назначением поля. Кнопка запуска без цены — прогноз включён в тариф; условия списания показываются до нажатия, не после (§5.2).
- Черновик сохраняется при закрытии — подписано в футере.

### 2.2 Шаблон «Форма» S11b (план §5.2)
- Свои данные — read-only строки с «Изменить» (сверка перед запуском), партнёр — ввод с нуля.
- Честность данных: если время рождения партнёра неизвестно — `role=alert`-подсказка «точность по домам снижена, об этом будет сказано в разборе». Не прячем ограничение за бейджем.
- Цена на кнопке («Построить разбор · 120 ✦») и условия списания до нажатия. Черновик привязан к разговору (§5.3), подписано.

### 2.3 Жизненный цикл выполнения S11c (план §5.3)
- Статусная строка + этапы (проверка доступа → расчёт → сборка → разбор агента) с состояниями done/active/pending (`aria-current="step"`).
- «Закрытие экрана не отменяет операцию» — подпись на экране; статус живёт в разговоре, результат приходит в ленту.
- Защита от двойного запуска: кнопка disabled во время выполнения.
- Слой сбоя (`?fail=1`): «Списание уже прошло — не повторяй платный запуск вслепую», действия «Проверить статус» / «Повторить». Сверка статуса до повторного списания — требование §5.3, помечено для Frontend.

### 2.4 Результат S12 (план §5.4)
- Единая структура: заголовок+агент+дата+номер разбора+данные → короткий вывод «Главное» → основной визуал → раскрываемые подробности → действия.
- Подробности — `<details>` (сферы совместимости открыты, полный разбор и ограничения — свернуты); mobile — та же лента, без вкладок.
- Ограничения точности — отдельный блок: «дома и куспиды не считались» (§10, честные ограничения). Это прямое продолжение подсказки S11b.
- Действия: «Обсудить с Уранией» (связанный диалог) / «В библиотеку». Сохранение в библиотеку — без повторного списания при открытии.

### 2.5 Таро: вопрос S13a (план §6.1–6.2)
- Короткое поле вопроса + 3 редактируемых примера-подстановщика.
- Строки выбора «Расклад» и «Колода» — отдельные ряды, возврат и смена возможны до вытягивания карт. Расклады — все активные, без ограничения тремя (§6.2).
- Тариф: «Расклад включён в тариф. Отдельно оплачивается только личный смысл» — условия до действия.

### 2.6 Таро: draw и раскрытие S13b (план §6.3–6.4)
- Фаза draw: веер из 5 рубашек + статус «Колода собирает твой расклад…». Выбор конкретной карты из 78 не изображается — его нет в контракте (§6.3, честность сцены).
- Фаза reveal: счётчик «Открыто N из 3», раскрытие по порядку позиций; вне порядка — инлайн-тост «Открывай карты по порядку…» (не тихий игнор). Позиция карты подписана; значение позиции открывается вместе с картой.
- Открытая карта → увеличенный просмотр (§6.5); повторное открытие не меняет карту.
- «Показать сразу» — равнодоступная альтернатива, тот же серверный набор (reading_id).
- Гейт интерпретации: «Личный смысл расклада — 80 ✦» с явным «оплачивается отдельно от вытягивания»; карты и порядок сохранены — можно вернуться и дочитать.

### 2.7 Таро: увеличенный просмотр S13c и разбор S13d (план §6.5–6.6)
- Zoom: карта крупно, имя + позиция + ориентация, значение карты; возврат без потери состояния сцены (счётчик и раскрытые карты сохранены); порядок не перетасовывается при ресайзе/возврате из оплаты.
- Разбор: сначала итог (verdict-блок), затем каждая карта по позиции с тенью; действия «Обсудить расклад в чате» / «В библиотеку». Повторное открытие — без нового draw и списания (§6, TAROT_REPLAY_CONTRACT).

### 2.8 Состояния §11.2 в пакете
Нарисованы: layer сбоя выполнения S11c (`?fail=1`), alert-подсказка неполных данных S11b, loading-фазы (draw-сцена, статус выполнения), disabled-кнопка запуска, empty-инлайн тосты. Полная матрица состояний S01–S30 — пакет 3.

## 3. Фон и силуэт (R05 rev2, без новых генераций)
`.sky[data-bg="chat"]` — единый режим для всех видов пакета: `bg-cosmos.jpg`, звёзды, приглушённый силуэт. Motion-хореография — после финального R05 (BUS-733).

## 4. Доступность (R03 §8.2, WCAG 2.1 AA)
- Focus-visible: `--focus-ring` на всех интерактивных (ряды конфигурации, карты, кнопки).
- Раскрытие карт: `button` с `aria-pressed` (false→true) и aria-label «Открыть карту: <позиция>»; счётчик — текст с живым значением.
- Alert'ы: неполные данные S11b и слой сбоя S11c — `role=alert`; статус выполнения — `role=status`; этапы — `aria-current="step"`.
- Примеры вопросов — кнопки (не ссылки), подстановка без отправки; zoom-возврат — явная кнопка «К раскладу».
- Контраст: тексты поверх surface-подложек; рубашки карт — декоративные (`alt=""`/`aria-hidden`).

## 5. Верификация (выполнено)
- 320px probe (iframe 320px, `scrollWidth` + элементы за 320.5px): **0 переполнений на всех 8 видах** после фиксов §6 (инструмент: probe `probe-http.html`).
- Интерактивные DOM-пробы `probe-flows.html` (7 проверок): подстановка примера; draw → disabled → reveal; вне порядка — блок + warn; по порядку — открытие + счётчик «Открыто 1 из 3»; «Показать сразу» — «3 из 3», все открыты; `?fail=1` — слой сбоя виден.
- Колода: md5-сверка `img/tarot/*`, `card-back.jpg`, фонов с `miniapp/img/` — идентичны, сабжектов генерации нет.
- Визуальная приёмка скриншотов — за EL/FE (vision-провайдер в ране недоступен).

## 6. Найти и фиксы (важно для Frontend)
1. **Обрыв CSS-каскада**: `.field__input` без закрывающей скобки отбрасывал все последующие правила до конца файла (`.sessions__*`, `.chat-header*`, `screenheader`, `.result*` и др.) — каскад «оживал» частично, экраны выглядели полуразобранными. Фикс: восстановлено правило по эталону p1. Урок: проверять баланс скобок CSS при генерации файла, а не только рендер «на глаз».
2. **`.screen` / `.tool-view` без `width:100%`+`min-width:0`** в flex-цепочке `screen-view → screen → tool-view` → `date-seg` из трёх инпутов растягивал tool-view до 332px. Фикс: `width:100%; min-width:0` на обоих + `min-width:0` на `.date-seg__seg` и `.field__input`.
3. **`.result__visual` min-content 330px**: img с inline `max-width:280px` не сжимался (min-content картинки = intrinsic), раздувал `.result` до 362px. Фикс: `max-width:min(280px,100%); min-width:0` на img, inline-стиль убран из HTML.
4. **Полный набор перенесённых из p1 правил обязателен**: `[hidden]{display:none!important}`, `.screen-view.is-active{flex-direction:column}` — в p2 эти правила уже включены; при сборке прод-стилей держать их в одном файле.
